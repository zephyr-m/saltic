# Time and State v0

Этот документ фиксирует канон перед проектированием identity-object.

Главная мысль:

```text
физическая вещь живёт во времени
Box описывает состояние вещи в моменте
identity связывает состояния одной вещи во времени
time является свойством среды исполнения, а не синтаксисом
```

## Проблема

Если добавить object identity без модели времени, язык начнёт прятать время в случайные места:

- `next_*` переменные;
- assignment;
- hidden mutation;
- runtime handles;
- trace;
- порядок вызовов;
- object references.

Это делает модель похожей на обычную mutable-программу, а не на физическую среду.

## Канон

Для физической модели S разделяет пять понятий:

```text
state       состояние в моменте
identity    непрерывность вещи через состояния
input/event причина перехода
transition  переход состояния
observation наблюдение состояния
```

Время не является переменной в пользовательской программе.

Время не является loop index.

Время не является `std.time` helper.

Время является базовым свойством engine/runtime-среды: она упорядочивает переходы, хранит причинность и даёт возможность наблюдать состояние как последовательность моментов.

Минимальная формула:

```text
state(t) + input(t) -> state(t + 1)
```

Текущий sandbox-loop уже является прототипом этой формулы:

```s
@lab = Laboratory {}

drum (std.group.count(inputs)) {
    @input = std.group.at(inputs, index)
    lab = dispatch(lab, input)
    render(lab)
    index = index + 1
}
```

Это ещё не финальная модель времени. Но это лучше, чем ручной сценарий, потому что программа обрабатывает поток входов.

В этом примере `drum` не создаёт время сам по себе. Он только даёт ранний способ проверить последовательность переходов. Настоящая модель времени должна принадлежать среде, которая исполняет переходы и хранит history.

## Time

В S время должно быть ближе к физике, чем к API.

Канон v0:

```text
time = порядок состояний и переходов в среде
```

Среда должна знать:

```text
moment
previous state
input/event
transition
next state
observation
```

Пользовательский код не обязан вручную считать время, если среда уже исполняет шаги.

Если в программе появляется ручное:

```s
@time = 0
time = time + 1
```

это признак, что мы временно моделируем то, что позже должно стать обязанностью engine/runtime.

## Engine responsibility

Минимальная ответственность будущей среды:

```text
принять input
найти текущее состояние
применить transition
создать следующий момент
сохранить history
дать observation
```

Язык описывает формы состояния и правила перехода.

Среда несёт время, порядок и историю.

## Local rhythm

У среды один общий порядок времени.

Но объект может иметь локальный ритм относительно времени среды.

Локальный ритм не измеряется в тиках.

Локальный ритм является коэффициентом:

```text
local rhythm = local time / environment time
```

Примеры:

```text
rhythm 1.0   объект живёт в темпе среды
rhythm 0.5   локальное время объекта идёт в два раза медленнее
rhythm 2.0   локальное время объекта идёт в два раза быстрее
rhythm 0.0   объект внутренне заморожен, но остаётся в causality среды
```

Это не создаёт отдельную вселенную времени.

Это определяет, сколько локального времени объект переживает относительно среды.

```text
environment moment -> object local progress
```

Объект с медленным ритмом может получать внешние события в общем порядке среды, но его внутренние процессы идут медленнее.

Объект с быстрым ритмом может выполнить больше внутренних изменений между наблюдаемыми моментами среды.

## Causality

Локальный ритм не должен ломать причинность.

Канон:

```text
один общий порядок событий
много локальных скоростей переживания времени
```

Если два объекта взаимодействуют, событие взаимодействия принадлежит времени среды.

Локальные ритмы влияют на внутреннее состояние объектов, но не отменяют общий порядок причин и следствий.

## Box

`Box` не должен становиться объектной системой.

Для физической модели:

```text
Box = форма состояния
```

Пример:

```s
Door = Box {
    state = DoorState.CLOSED
}
```

`Door {}` — это не вся дверь как вечная сущность.

Это состояние двери в конкретном срезе вычисления.

Физическая дверь как identity должна связывать такие состояния во времени:

```text
door@t0 = Door { state = CLOSED }
door@t1 = Door { state = CLOSED }
door@t2 = Door { state = OPEN }
```

## Drum

`drum` сейчас остаётся единственной базовой формой повторения.

Не добавлять `drum tick (...)` только ради индекса.

Не расширять цикл, чтобы имитировать время.

Если время появляется в S как полноценная часть системы, оно должно быть свойством engine/runtime, а не удобной переменной внутри `drum`.

## Identity-object

Не проектировать identity-object отдельно от времени.

Identity-object должен отвечать не только:

```text
это та же вещь?
```

Но и:

```text
какое состояние этой вещи в данном моменте?
какая история привела к этому состоянию?
какое событие вызвало переход?
```

До этого момента `Box` остаётся value container для состояния.

## Не входит в v0

- новый синтаксис времени;
- automatic tick variable;
- `drum tick`;
- ручной clock API как основа модели;
- mutable object fields;
- field assignment;
- hidden object mutation;
- event scheduler;
- real-time clock;
- physical time units;
- history storage format.

## Практическое правило

Сначала менять модель программы.

Добавлять синтаксис только если несколько runnable tasks подряд показывают одну и ту же нехватку.

Следующие sandbox tasks должны явно различать:

- состояние;
- вход;
- переход;
- наблюдение;
- историю или порядок шагов.

Но они не должны вводить синтаксис времени, пока не станет ясно, какая часть должна жить в языке, а какая в engine/runtime.
