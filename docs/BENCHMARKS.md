## Как мерили

Исходники всех задач на всех языках — `docs/benchmarks/` (`fib.*`,
`binary-trees.*`, `fannkuch.*`), ожидаемый вывод — `*.expected`.

- Машина: Acer, Intel Core i5-12450H, NixOS; один поток.
- Время — лучшее из 3 запусков (`/run/current-system/sw/bin/time`, `%e`),
  память — пик RSS (`%M`).
- Saltic собран компилятором с полки. До 154:47:128 цель `x86_64` — машинный
  код RV32I, переведённый в x86-64; с 154:47:128 — родной бэкенд x86-64
  (строки «родной»). «Saltic, QEMU» — RV32I под `qemu-riscv32`.
- Языки: C — GCC 14.3 (`-O2`, `-O0`); Node 24.18; PHP 8.4.22 (JIT —
  `opcache.jit=tracing`); Lua 5.4.9; LuaJIT 2.1; Ruby 3.4.11 (YJIT —
  `--yjit`); Python 3.13.12.

## Что видно

- **Память** — у Saltic лучшая или почти лучшая везде: 9 МБ на
  binary-trees против 47–108 МБ у интерпретаторов и JIT, меньше 1 МБ на
  fannkuch (массивы на `core.bytes`).
- **Вызовы и арифметика** (fib) — родной x86-64 в 2,6 раза быстрее
  перевода: рядом с Node и Ruby+YJIT, обгоняет PHP с JIT; впереди только C и
  LuaJIT.
- **Массивы** (fannkuch) — родной вдвое быстрее перевода: между PHP с JIT и
  обычным PHP, вдвое быстрее Lua 5.4, в 17 раз быстрее Python.
- **Мелкие объекты** (binary-trees) — слабое место: и родной (3,28 с), и
  перевод — последние, в 20 раз медленнее C; родной бэкенд тут почти не
  помог, упор не в команды, а в выделение памяти. Каждая группа из двух элементов — выделение памяти, регион,
  проверки. Сюда смотреть первым на этапе оптимизаций (`docs/PLAN.md`,
  «Скорость»: анализ побега, встраивание, дешёвое выделение).
