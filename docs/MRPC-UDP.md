# mRPC/1.0 поверх UDP

Черновик раздела «UDP (optional)» для спецификации mRPC (автор протокола —
Зэф, github.com/zephyr-m/mRpc, `SPEC.md`). Решение автора 04.11.2026:
дописать в спецификацию; пока раздел живёт здесь, перенос — пункт в
[PLAN.md](PLAN.md). Реализация в Saltic: `os/target/uefi_x86_64/network/mrpc.saltic`
(агент Acer и программы с сетью), мост `os/target/uefi_x86_64/tools/mrpc_bridge.py`.

Ключевые слова MUST / SHOULD / MAY — по RFC 2119, как во всей спецификации.

## 1. Когда

UDP — транспорт для устройств без TCP-стека: прошивки, микроконтроллеры,
голое железо. Запрос и ответ — те же объекты JSON, что в HTTP (§3 SPEC);
меняется только доставка.

## 2. Сообщение

- Одна датаграмма — ровно одно сообщение: один объект JSON, UTF-8, без
  обёрток и разделителей. Склейки нескольких датаграмм в одно сообщение
  нет.
- Сервер MUST отличать сообщение mRPC по первому непробельному байту `{`.
  Всё остальное он MAY обрабатывать своим протоколом на том же порту
  (в Saltic — старые текстовые команды агента).
- Ответ уходит на адрес и порт, с которых пришёл запрос.
- Строки ответа SHOULD передаваться UTF-8 как есть, экранируются только `"`,
  `\` и управляющие знаки (`\n`, `\r`, `\t`, прочие — `\u00XX`) — так русский
  текст занимает вдвое меньше, чем через `\uXXXX`.

```json
→ {"cmd":"info","id":7}
← {"ok":true,"cmd":"info","id":7,"v":"mRPC/1.0","ms":0,"data":{"agent":13}}
```

## 3. `id`

- UDP теряет и переставляет датаграммы, поэтому клиент SHOULD ставить `id`
  в каждый запрос и MUST сверять `id` ответа с запросом; ответ с чужим `id`
  клиент отбрасывает.
- Сервер MUST вернуть `id` запроса без изменений (строку — строкой, число —
  числом) и MUST NOT добавлять `id`, если его не было.
- Повтор запроса после тишины — дело клиента; сервер SHOULD держать команды
  чтения (`query`) безопасными для повтора.

## 4. Размер и обрезка

- Ответ MUST помещаться в одну датаграмму без фрагментации IP: предел
  сервера (`limit`) SHOULD быть не больше 1400 байт.
- Если `data.text` не влезает, сервер MUST обрезать текст по границе знака
  UTF-8 (не посреди буквы и не посреди экранирования) и добавить
  `"cut": true` в `data`. Остальные поля ответа обрезке не подлежат.
- Объектные `data` сервер SHOULD строить так, чтобы они влезали; если
  объект не влезает — ошибка `internal` с объяснением в `message`.

```json
← {"ok":true,"cmd":"volumes","v":"mRPC/1.0","ms":0,"data":{"text":"том 0: …","cut":true}}
```

## 5. `help` страницами

Полный `help` с описаниями обычно не влезает в датаграмму (§7.1 SPEC).

- Запрос MAY содержать `from` — номер первой команды страницы (с нуля).
- Сервер кладёт в `data.commands` столько команд с `description`, сколько
  влезает, начиная с `from`; `data.total` — число всех команд; если
  отданы не все — `data.next` с номером следующей.
- Клиент повторяет `help` с `from = next`, пока `next` не пропадёт.
  Сервер без поддержки `from` отдаёт всё сразу — клиент получит страницу без
  `next` и закончит.

```json
→ {"cmd":"help","from":0}
← {"ok":true,"cmd":"help","v":"mRPC/1.0","ms":0,"data":{"commands":{…},"total":24,"next":12}}
→ {"cmd":"help","from":12}
← {"ok":true,"cmd":"help","v":"mRPC/1.0","ms":0,"data":{"commands":{…},"total":24,"next":21}}
→ {"cmd":"help","from":21}
← {"ok":true,"cmd":"help","v":"mRPC/1.0","ms":0,"data":{"commands":{…},"total":24}}
```

## 6. `ms`

`ms` MUST присутствовать (§3.4 SPEC). Если часы устройства не знают долей
секунды (так у прошивки Acer), сервер MAY отдавать время кратным 1000 —
и тогда почти всегда `0`.

## 7. Параметры с необязательными

Реестр команды MAY перечислять необязательные параметры отдельно от
обязательных: `"params": ["address"]` — обязательные (§6.3 SPEC),
`"options": {"bytes": null}` — необязательные. Смешанного вида в §6.3 нет;
поле `options` — расширение.

## Ещё не решено

- Длинные ответы несколькими датаграммами (например, снимок экрана сейчас
  идёт отдельным текстовым протоколом `shot-part`).
- Событие от сервера без запроса (аналог §10.5 Server Push) по UDP.
