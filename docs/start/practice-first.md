# Practice-first ограничения

Этот документ защищает S от бесконечной разработки самого языка.

S должен как можно раньше перейти от вопроса "каким будет язык" к вопросу "легко ли на нём решить реальную задачу".

## Главное правило

Каждый следующий шаг после рабочего parser/checker/runtime должен давать одну из двух вещей:

- полезную программу на S;
- минимальную правку языка/tooling, без которой эта программа не может быть написана нормально.

Если изменение не связано с конкретной программой, оно уходит в backlog.

## Что считается полезной программой

Полезная программа на S:

- запускается через `just run-file examples/<name>.s`;
- делает понятную работу без чтения исходников Racket;
- использует обычный файл, строку, число, список действий или trace;
- имеет короткое описание рядом с примером;
- может быть объяснена командой `just explain examples/<name>.s`.

Минимальная полезность важнее масштаба. Скрипт, который считает строки, сортирует записи или проверяет дневной финансовый лог, ценнее новой абстрактной подсистемы без пользователя.

## Стоп-правило

Нельзя брать большую языковую задачу, пока нет хотя бы одного нового практического `.s`-примера из текущего цикла.

Большая языковая задача:

- новый синтаксис;
- новая модель типов;
- IR;
- backend;
- package manager;
- крупный runtime слой;
- новая доменная библиотека;
- спор о названии конструкции дольше одной рабочей сессии.

Исключение: bugfix, диагностика, formatter или один маленький host primitive, если без него блокируется ближайшая полезная программа.

## Бюджет на язык

На одну полезную программу разрешается не больше одного маленького изменения языка или tooling.

Примеры допустимых изменений:

- добавить понятную diagnostic;
- починить parser для уже выбранного синтаксиса;
- добавить один `host.file` или `host.str` primitive;
- расширить `explain`, чтобы программа была понятнее;
- добавить formatter rule для уже существующей конструкции.

Если для программы нужно три или больше изменений языка, задача слишком большая. Нужно выбрать более маленькую программу.

## Первый практический milestone

Перед следующим крупным этапом S должен иметь три маленькие полезные программы:

```text
examples/user/count-lines.s
examples/text-summary.s
examples/user/finance-log.s
```

Смысл:

- `count-lines.s` доказывает работу с файлами;
- `text-summary.s` доказывает работу со строками и простым выводом;
- `finance-log.s` связывает язык с реальной личной задачей: считать простой баланс прихода и расхода без доработки bootstrap runtime.

Каждая программа должна:

- парситься;
- проходить checker;
- запускаться;
- объясняться через `just explain`;
- быть достаточно простой, чтобы её можно было переписать по памяти.

## Что откладывается

До завершения первого практического milestone не начинать:

- IR;
- внешний backend;
- самохостинг;
- package manager;
- большую std;
- большую `core.*` карту;
- сложную систему типов;
- новые доменные ядра;
- расширенный world engine.

World остаётся важной целью, но следующий шаг должен доказать, что S удобен для маленькой реальной программы, а не только для красивой архитектуры.

## Definition of done для v0.1 practice

Практический этап считается пройденным, когда:

- есть три полезные программы;
- каждая запускается одной командой;
- ошибки по ним понятны без чтения Racket;
- README показывает, какую реальную задачу уже можно решить на S;
- дальнейшие изменения языка идут от боли этих программ, а не от абстрактного желания достроить идеальный язык.
