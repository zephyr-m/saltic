# Task lessons

Этот документ фиксирует выводы из реальных task-листов.

Правило: если задача показала нехватку языка, сначала записать наблюдение, а потом решать, нужна ли новая возможность.

## 001 finance balance

Что подтвердилось:

- `skill` хорошо читается как маленькое действие.
- `program()` хорошо отделяет исполнимый вход от вспомогательных действий.
- `use std` достаточно лёгкий для пользовательского кода.

Вывод:

- простая вычислительная задача уже читается как лист, а не как технический скрипт.

## 002 energy day

Что подтвердилось:

- для физической модели сразу понадобились сравнения `>` и `<`;
- `enum` хорошо подходит для статуса процесса: `SAFE`, `LOW`;
- `std.io.println` явно показывает наблюдаемый вывод.

Что обнаружено:

- точные дроби печатаются как `95/2`;
- это сохраняет точность, но для человеческого вывода позже понадобится явный формат чисел.

Вывод:

- сравнения являются фундаментальной частью процесса, а не синтаксическим сахаром;
- формат чисел должен быть явным, а не скрытой магией runtime.

## 003 energy week

Что подтвердилось:

- `drum (days)` читается нормально для повторяемого физического шага;
- состояние можно обновлять внутри цикла без дополнительного синтаксиса;
- модель `state -> repeated action -> observation` уже выражается текущим S.

Что обнаружено:

- индекс шага не обязан быть частью `drum`;
- если процессу нужен счётчик, его можно сделать явным состоянием: `@day = 1`, затем `day = day + 1`;
- это сохраняет `drum` маленьким и делает состояние процесса видимым.

Вывод:

- `drum` можно оставить как минимальный повтор;
- индекс `drum` пока не нужен как фича языка;
- если будущая форма цикла появится, она должна быть сильнее явного состояния, а не просто короче.

## Открытые кандидаты

Не добавлять автоматически. Проверять через новые tasks.

- явный формат чисел;
- комментарии, если листу нужна встроенная человеческая пояснительная строка;
- единицы измерения, если задачи начнут путать Wh, %, дни и деньги.

## 004 render frame

Что подтвердилось:

- S хорошо читает простую render-логику: камера, координаты, радиус, видимость;
- `enum` подходит для состояния объекта: `VISIBLE`, `HIDDEN`;
- математическая часть кадра читается без лишней нагрузки.

Что обнаружено:

- без `Box` объект приходилось бы передавать как набор параметров: `name, x, y, visibility`;
- `Box v0` делает сцену заметно ближе к предметной модели: `Point`, `Frame`, `Camera`, `Object`;
- отсутствие настоящего canvas пока не мешает первому render task, потому что текстовый кадр достаточно проверяем.

Вывод:

- render-домен стал первым практическим основанием добавить `Box v0` в язык;
- следующий render task должен проверить коллекции объектов или настоящий кадр, а не только отдельные значения.

## 005 render scene group

Что подтвердилось:

- сцена естественно читается как группа объектов;
- `Box` и `Group` хорошо складываются: `Box` описывает форму вещи, `Group` описывает несколько вещей;
- `drum` достаточно для обхода группы, если индекс является явным состоянием.

Что обнаружено:

- отдельный `each` сейчас не нужен;
- `list`, `array` и `set` несут лишние исторические или математические ожидания;
- имя `Group` лучше совпадает с моделью цифрового мира на текущем этапе.

Вывод:

- добавлен `Group v0`: литерал `[...]`, `std.group.count`, `std.group.at`;
- `Group v0` не является системным массивом и не решает layout памяти;
- повторение остаётся через `drum`, чтобы язык не плодил формы цикла.

## 006 object module

Что подтвердилось:

- объекту нужен отдельный лист, если у него есть состояния, события и реакция;
- `Box` остаётся формой вещи, а `skill react(...)` описывает допустимый transition;
- `use objects.player` достаточно для первого разделения большого файла на объектный модуль и сценарий.

Что обнаружено:

- методы вида `player.react(move)` пока не нужны;
- private/public пока не нужны;
- object module v0 должен быть файловой организацией, а не новой объектной системой.

Вывод:

- добавлен local module loader для `use objects.player`;
- импорт ищет `objects/player.s` относительно текущего файла;
- следующий шаг в объектной модели должен проверять несколько объектов или несколько событий, а не добавлять синтаксис методов.

## 007 object reaction chain

Что подтвердилось:

- текущего языка уже хватает, чтобы выразить объектный автомат без новой фичи;
- цепочка событий хорошо читается как `Group`;
- `drum` подходит для последовательного применения событий;
- объект меняется только через `react(current, event)`, а не через прямое изменение поля.

Что обнаружено:

- `react` как свободный skill рядом с объектом пока достаточно понятен;
- `Event` как `Box` с `kind` и параметрами работает для первого автомата;
- отсутствие методов и private/public не мешает первому практическому примеру.

Вывод:

- не добавлять field assignment как следующий шаг только ради удобства;
- не добавлять `player.react(...)`, пока обычный `react(player, event)` решает задачу;
- следующий объектный task должен проверить несколько объектных модулей или взаимодействие объектов.

## 008 object interaction

Что подтвердилось:

- два object modules уже могут взаимодействовать через события;
- объект может передавать другому объекту не себя целиком, а наблюдаемое состояние;
- `react_player` и `react_door` читаются достаточно явно для первого взаимодействия.

Что обнаружено:

- текущий import вливает top-level имена в общий файл;
- чтобы избежать конфликтов, приходится писать явные имена вроде `PlayerState`, `DoorState`, `react_player`, `react_door`;
- это работает, но показывает будущую необходимость namespace-модели.

Вывод:

- namespace для object modules пока не надо добавлять вслепую;
- следующий тест на модули должен намеренно проверить конфликт имён или предложить канон имён;
- текущая объектная модель уже позволяет строить простые причинные цепочки между объектами.

## 009 laboratory sandbox loop

Что подтвердилось:

- песочница читается лучше как поток `Input`, а не как ручной сюжет;
- `dispatch(lab, input)` становится центральной точкой перевода ввода в изменение состояния;
- `render(lab)` отделяет наблюдение от правил изменения;
- текущего языка хватает для первого sandbox-loop без новых фич.

Что обнаружено:

- код всё ещё пересобирает `Laboratory` после каждого ввода;
- это терпимо для v0, но не является настоящей identity/reference моделью;
- enum выводится полным именем состояния, например `LockState.UNLOCKED`.

Вывод:

- следующий шаг не обязан быть новым синтаксисом;
- полезнее проверить несколько разных input-последовательностей или недопустимое действие;
- модель `inputs -> dispatch -> render` ближе к будущей песочнице, чем заранее расписанный сценарий.

## Time and state note

Что стало ясно после 009:

- identity-object нельзя проектировать отдельно от времени;
- `Box` лучше трактовать как форму состояния в моменте, а не как всю вещь;
- `lab = dispatch(lab, input)` выглядит как value-модель, но физически это прототип `state(t) + input(t) -> state(t + 1)`.

Вывод:

- перед identity-object зафиксирован [Time and State v0](../spec/time-state-v0.md);
- не добавлять скрытый `tick` в `drum`;
- не превращать время в ручной счётчик;
- считать время свойством engine/runtime-среды;
- не добавлять field assignment как замену модели времени;
- следующие sandbox tasks должны проверять state/input/transition/observation, а не просто удобство мутации.

## 010 laboratory history

Что проверяет:

- лаборатория читается как последовательность наблюдаемых моментов;
- `dispatch(lab, input)` остаётся transition-точкой;
- `observe(moment, input, lab)` отделяет наблюдение от изменения состояния;
- вывод показывает input, состояние замка и состояние двери для каждого шага.

Что важно:

- `moment` в задаче является временной переменной теста, а не новой моделью времени;
- задача не добавляет синтаксис времени;
- задача подтверждает, что текущий S уже может описывать `input -> transition -> observation`.

Вывод:

- следующий большой шаг всё ещё не обязан быть синтаксисом;
- можно двигаться к identity-object или к `S scene -> visual observation`;
- если появится ещё несколько задач с ручным `moment`, это будет сигнал переносить порядок моментов в engine/runtime.

## 011 visual observation protocol

Что проверяет:

- S может описать наблюдаемую инженерную сцену без HTML;
- runtime может выдать backend-neutral visual trace;
- первый primitive `square_bipyramid` связывает текстовую модель с будущим живым чертежом;
- `visual.trace()` отделяет описание наблюдения от конкретного renderer.

Что важно:

- это не canvas API;
- это не browser API;
- это не финальная стандартная библиотека;
- это первый протокол между S-сценой и будущим display backend.

Вывод:

- практический путь к "цифровой бумаге" начинается с `S scene -> visual trace`;
- временный HTML preview можно делать позже поверх trace, не внутри языка;
- следующий визуальный шаг должен быть backend для trace, а не расширение синтаксиса.

## 012 actor fabric pulse

Что проверяет:

- акторную модель можно набросать обычным S без новых runtime intrinsics;
- leaflet можно представить как `Box`;
- actor state можно менять через transition skills;
- вычисление читается как два момента взаимодействия.

Что обнаружено:

- доставка сообщения пока ручная;
- `Fabric` пересобирается как value state;
- нет настоящих inbox/outbox group operations;
- направление уже читается, но код показывает будущую потребность в actor fabric layer.

Вывод:

- `computation = interaction over time` подтверждается runnable-задачей;
- не добавлять `actor.*` в runtime до нескольких таких tasks;
- следующий actor step должен проверить группу leaflets или простейшую delivery очередь.
