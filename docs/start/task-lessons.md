# Task lessons

Этот документ фиксирует выводы из реальных task-листов.

Правило: если задача показала нехватку языка, сначала записать наблюдение, а потом решать, нужна ли новая возможность.

## 001 finance balance

Что подтвердилось:

- `skill` хорошо читается как маленькое действие.
- `program()` хорошо отделяет исполнимый вход от вспомогательных действий.
- `use std` достаточно лёгкий для пользовательского кода.

Вывод:

- простая вычислительная задача уже читается как лист, а не как технический скрипт.

## 002 energy day

Что подтвердилось:

- для физической модели сразу понадобились сравнения `>` и `<`;
- `enum` хорошо подходит для статуса процесса: `SAFE`, `LOW`;
- `std.io.println` явно показывает наблюдаемый вывод.

Что обнаружено:

- точные дроби печатаются как `95/2`;
- это сохраняет точность, но для человеческого вывода позже понадобится явный формат чисел.

Вывод:

- сравнения являются фундаментальной частью процесса, а не синтаксическим сахаром;
- формат чисел должен быть явным, а не скрытой магией runtime.

## 003 energy week

Что подтвердилось:

- `drum (days)` читается нормально для повторяемого физического шага;
- состояние можно обновлять внутри цикла без дополнительного синтаксиса;
- модель `state -> repeated action -> observation` уже выражается текущим S.

Что обнаружено:

- индекс шага не обязан быть частью `drum`;
- если процессу нужен счётчик, его можно сделать явным состоянием: `@day = 1`, затем `day = day + 1`;
- это сохраняет `drum` маленьким и делает состояние процесса видимым.

Вывод:

- `drum` можно оставить как минимальный повтор;
- индекс `drum` пока не нужен как фича языка;
- если будущая форма цикла появится, она должна быть сильнее явного состояния, а не просто короче.

## Открытые кандидаты

Не добавлять автоматически. Проверять через новые tasks.

- явный формат чисел;
- комментарии, если листу нужна встроенная человеческая пояснительная строка;
- единицы измерения, если задачи начнут путать Wh, %, дни и деньги.

## 004 render frame

Что подтвердилось:

- S хорошо читает простую render-логику: камера, координаты, радиус, видимость;
- `enum` подходит для состояния объекта: `VISIBLE`, `HIDDEN`;
- математическая часть кадра читается без лишней нагрузки.

Что обнаружено:

- без `Box` объект приходилось бы передавать как набор параметров: `name, x, y, visibility`;
- `Box v0` делает сцену заметно ближе к предметной модели: `Point`, `Frame`, `Camera`, `Object`;
- отсутствие настоящего canvas пока не мешает первому render task, потому что текстовый кадр достаточно проверяем.

Вывод:

- render-домен стал первым практическим основанием добавить `Box v0` в язык;
- следующий render task должен проверить коллекции объектов или настоящий кадр, а не только отдельные значения.
