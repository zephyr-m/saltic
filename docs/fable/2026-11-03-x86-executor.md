## Коротко

- Окно гостя: `r14` — база, все роли — 32-битные значения в 32-битных
  регистрах; запись 32-битной командой обнуляет старшую половину, поэтому
  `[r14 + роль + смещение]` — одна команда без подготовки. [предп.]
- `STACK` = `rsp` (настоящий 64-битный указатель внутри окна), `call`/`ret` —
  родные; роль `RETURN` живёт на стеке там, куда её положил `call`, и
  регистра не занимает; `store/load` роли `RETURN` — пустые операции.
  Держится на дисциплине, которую код RV32I уже соблюдает: перед `ret` стек
  возвращён на место, `ra` нигде не значение. [чтение `functions`, рантайм]
- Регистров под роли — 14 (16 минус `r14`, `rsp`); ролей, которым нужен
  регистр, — 21 из 23. Исполнитель умеет держать холодные роли в памяти
  (слова bss `saltic_roles`, операнд `[r14 + disp32]`), так что любой итог
  сжатия шага 3 от 14 до 21 роли собирается; быстро — только регистры.
- Код x86 лежит **внутри окна гостя** по тем же адресам, что RV
  (`layout.host`: 65536): `load_address` любой метки — `mov r32, imm32`,
  косвенных переходов и таблиц нет, ELF64 — это ELF32 хоста, сдвинутый на
  4 ГиБ; PE — одна секция, `r14 = image_base`. [предп.]
- Метки и переходы: один проход, все переходы `rel32` фиксированной длины,
  два новых нейтральных вида патча в `layout` (`REL32`, `ABS32`).
  Двухпроходная раскладка не нужна. [чтение `layout`]
- Готовые байты `SYSCALL_STUB`/`ENTRY_*` разобраны дизассемблером [проба] —
  их смысл записан в §4; переписать через кодировщик можно без догадок.
- Прогноз: ~1 950 новых строк в `backend/x86_64_native/` и рядом
  (кодировщик ~400, исполнитель ~450, образы ~300, Linux ~200, UEFI ~350,
  нить `state`/тесты ~80, скрипты ~100). Восемь малых шагов, у каждого
  приёмка (§5).

## 1. Карта ролей → регистры x86-64

### Принципы

1. **Роль = 32-битный регистр.** Каждая запись в роль — 32-битная команда
   (`mov r32`, `add r32`, `movzx`, `setcc + movzx`); старшая половина
   обнуляется железом, и 64-битное чтение того же регистра — готовый
   беззнаковый адрес гостя. Адресация: `[r14 + base64 + disp32]`.
2. **`STACK` = `rsp`**, 64-битный хост-указатель `r14 + sp_гостя`. Роль
   читается как значение в четырёх местах (`_start`, `rescue`, пролог
   `FRAME = STACK + frame`, `push/pop`) — каждому своя последовательность
   (§2). Требования «младшие 32 бита `r14` равны нулю» нет: вычитание
   `r14` явное, на UEFI база любая.
3. **`RETURN` без регистра.** `call` = `call rel32` (8 байт на стеке),
   `ret` = `ret`. `store(RETURN, …)` / `load(RETURN, …)` — пустые. Кадр
   получает 8 скрытых байт над `FRAME` (между `call` и `sub rsp, frame`);
   раскладка `constants` не меняется, слот `RETURN` остаётся пустым.
   Условие: перед `ret` `rsp` стоит там, где был сразу после `call`, —
   кодоген (`functions`), `compile_constant`, диспетчеры и все `rt_*` это
   соблюдают (grep: `ra` только в `sw/lw ra` и `jalr ra`). [чтение]
4. **Бюджет — 14 регистров**: `rax rcx rdx rbx rbp rsi rdi r8–r13 r15`.
   Горячие роли — в семь коротких (без REX) регистров.
5. **Что портят чужие соглашения** [чтение ABI]:
   - Linux `syscall`: `rax` (результат), `rcx`, `r11`; аргументы
     `rdi rsi rdx r10 r8 r9`.
   - Вызов прошивки UEFI (MS x64): `rax rcx rdx r8 r9 r10 r11`, `xmm0–5`;
     `rsp` выровнен на 16, 32 байта тени; сохраняются `rbx rbp rsi rdi r12–r15`.
   Порчи закрываются внутри подпрограмм платформы (§2 `syscall`): они
   сохраняют `rcx`/`r11` (на UEFI — все летучие регистры-роли) на стеке
   гостя. Договор не меняется: «`syscall` портит только `VALUE`».

### Роли в памяти — как исполнитель их держит [предп.]

x86 допускает один операнд в памяти у `mov/add/sub/and/or/xor/cmp/test/
shl/neg` и запись `imm32` в память. Поэтому:

- источник в памяти — та же команда с операндом `[r14 + disp32]`;
- приёмник в памяти у `move/load_immediate/load_address` — `mov [slot], r32`
  / `mov dword [slot], imm32`; у арифметики — `mov [slot], left; add [slot],
  right`;
- `load(mem, base, off)` и два операнда в памяти — через `push rax; … ; pop
  rax` (+2 команды);
- база адреса в памяти (`load(to, ARGV, off)`) — `mov to, [slot]; mov to,
  [r14 + to + off]` (приёмник служит временным).

Запасной регистр не резервируется; холодная роль стоит 1–3 команды только
там, где встречается. Если шаг 3 ужмёт до 14 — механизм не задействуется,
но остаётся для Thumb-2 (13 регистров).

## 2. Операции договора → команды x86-64

Обозначения: `R(x)` — регистр роли, `M(x, off)` — `[r14 + R(x) + off]`
(для `STACK` — `[rsp + off]`), `L` — метка. Команды 32-битные, кроме
помеченных `(64)`.

### Программа и данные (9)

`new_program(entry)` → `layout.host(entry)` как у RV (адрес 65536, низкая
память 64 КиБ); `heap_size`, `label`, `data_label`, `align`, `data_byte`,
`data_word`, `data_text`, `reserve` — `layout` как есть (архитектуры в них
нет).

### Константы и адреса (3)

| Операция | x86 | Байт |
|---|---|---|
| `load_immediate(to, n)` | `mov R(to), imm32`; при `n == 0` — `xor R(to), R(to)` | 5–6 / 2–3 |
| `load_word(to, word)` | `mov R(to), word` | 5–6 |
| `load_address(to, L, addend)` | `mov R(to), imm32` + патч `ABS32` (адрес гостя метки + addend) | 5–6 |

`load_address` одинаков для кода, rodata, data, bss — всё в окне.

### Регистры (18)

| Операция | x86 |
|---|---|
| `move(to, from)` | `mov R(to), R(from)`; `move(to, STACK)`: `mov R(to)64, rsp; sub R(to)64, r14` (64); `move(STACK, from)`: `lea rsp, [r14 + R(from)]` (64) |
| `negate(to, from)` | `mov` при `to ≠ from`; `neg R(to)` |
| `add_immediate(to, from, n)` | `to == from`: `add R(to), imm8/32`; иначе `lea R(to), [R(from) + n]`; `add_immediate(STACK, STACK, n)`: `add/sub rsp, n` (64); `add_immediate(to, STACK, n)`: `lea R(to)64, [rsp + n]; sub R(to)64, r14` (64); `add_immediate(STACK, from, n)`: `lea rsp, [r14 + R(from) + n]` (64) |
| `add(to, l, r)` | `to == l`: `add R(to), R(r)`; `to == r`: `add R(to), R(l)`; иначе `lea R(to), [R(l) + R(r)]` (адресация 64, запись 32 — младшие биты верны) |
| `sub(to, l, r)` | `to == l`: `sub`; `to == r`: `neg R(to); add R(to), R(l)`; иначе `mov; sub` |
| `and / or / xor(to, l, r)` | как `add` (коммутативны), без `lea` |
| `and/or/xor_immediate(to, from, n)` | `mov` при `to ≠ from`; `op R(to), imm8/32` |
| `shift_left / shift_right_signed / shift_right_unsigned(to, from, n)` | `mov` при `to ≠ from`; `shl / sar / shr R(to), imm8` |
| `shift_left_by / shift_right_unsigned_by(to, from, count)` | `R(count) == ecx`: `mov; shl R(to), cl`; иначе `push rcx; mov ecx, R(count); mov; shl R(to), cl; pop rcx` (`to == ecx` — через `xchg`); 3 места в рантайме |
| `set_less(to, l, r)` | `cmp R(l), R(r); setl R(to)8; movzx R(to), R(to)8` (`cmp` раньше записи — `to == l/r` допустимо; `sil/dil/bpl` требуют REX) |
| `set_less_unsigned` / `set_less_unsigned_immediate` | `setb` |
| `set_zero(to, from)` / `set_nonzero` | `test R(from), R(from); sete/setne; movzx` |

### Проверенная арифметика (2)

`add_checked()`: `add eax, edx; jo .ovf; mov edx, CALL_NO_ERROR; jmp .done;
.ovf: mov edx, ERROR_NUMBER_OVERFLOW; .done:`. Флаг OF 32-битного сложения
— ровно то, что RV считает двумя `slt` (`(sum < a) != (b < 0)`); сумма в
`VALUE` в обоих случаях завёрнутая. `SCRATCH0…2` не портятся. `sub_checked`
— `sub; jo`. [чтение `rv32i.checked`]

### Память и стек (10)

| Операция | x86 |
|---|---|
| `load(to, base, off)` | `mov R(to), M(base, off)`; `load(STACK, base, off)`: `mov esp, M; add rsp, r14` (64) — на UEFI в обёртке `cli … sti` (риск 4) |
| `load_byte / load_half` | `movzx R(to), byte/word M` |
| `store(from, base, off)` | `mov M, R(from)`; `store(STACK, base, off)`: `push rcx; lea rcx, [rsp + 8]; sub rcx, r14; mov M, ecx; pop rcx` (только `rescue.enter`) |
| `store_byte / store_half` | `mov byte/word M, R(from)8/16` (REX для `sil/dil/bpl`; префикс `66` для полуслова) |
| `store_zero / store_byte_zero` | `mov dword/byte M, 0` |
| `push(from)` | `sub rsp, 4; mov [rsp], R(from)` — ячейка 4 байта, как в договоре (родной `push r64` — 8) |
| `pop(to)` | `mov R(to), [rsp]; add rsp, 4` |

### Переходы (16) и вызовы (3)

Близкие и дальние переходы договора становятся одним: `cmp/test` + `jcc
rel32` (6 байт) или `jmp rel32` (5), патч `REL32`. `branch_zero` — `test;
jz`; `branch_negative` — `js`; `branch_not_negative` — `jns`;
`branch_not_positive` (`bge x0, rs`) — `test; jle`; беззнаковые — `jb/jae`;
`jump_if_*` — то же без обратной ветки; `jump_far` — `jmp rel32` (`SCRATCH1`
не трогается); `call(L)` — `call rel32`; `ret()` — `ret`.

### Платформа (3)

- `syscall(number)` → `call x86_syscall_<number>` — подпрограмма, которую
  модуль платформы (Linux или UEFI) выпускает в код при записи образа (§4).
  Подпрограмма видит роли в регистрах, кладёт `VALUE, ERROR, ARG2…ARG5` в
  `rdi rsi rdx r10 r8 r9` (указатели — `lea rN, [r14 + rN]`), сохраняет
  `rcx`/`r11` на стеке гостя, результат — в `eax`. Неизвестный номер —
  `x86_syscall_unknown`, −38 (ENOSYS), как заглушка перевода (аудит 10.1:
  «не умею», не ловушка).
- `wait()` → Linux: `pause` (сейчас перевод даёт `ud2` → Illegal
  instruction); UEFI: `hlt` — настоящее «ждать прерывания», таймер прошивки
  будит. Решение автора (§6).
- `fence()` → `mfence`.

### Что берётся из `x86_64_translation/encoder.saltic`, что дописать [чтение]

Копией в свой `x86_64_native/encoder.saltic` (перевод остаётся нетронутым
оракулом): `bytes`, `signed_word`, `immediate32`, коды групп `ADD/OR/AND/
SUB/XOR/CMP`, сдвигов, условий, `jump/jump_condition/call` с нулевым
`rel32`, `set_condition`, `breakpoint`, `undefined` — ~70 строк.

Нынешний кодировщик привязан к `EAX/ECX/EDX` и файлу `r15` (`operate`,
`load_memory`, `store_memory` без REX для регистров ≥ 8). Нужен общий с
тремя строителями — `rex(w, reg, index, base)`, `modrm(mod, reg, rm)`,
`sib(scale, index, base)` — и правилами особых случаев (`rsp`/`r12` в базе →
SIB; `rbp`/`r13` без смещения → disp8 = 0; `[r14 + disp32]` без индекса).
На них ~25 навыков: `mov r,r`, `mov r,imm`, `mov r,[mem]`, `mov [mem],r`
(8/16/32/64), `mov [mem],imm32`, `movzx`, `lea` (64), `alu r,r / r,imm /
r,[mem] / [mem],r`, `shl/sar/shr r,imm / r,cl`, `neg`, `test`, `cmp`,
`setcc r8`, `jcc/jmp/call rel32`, `ret`, `push/pop r64`, `syscall`, `call
[r64 + disp]`, `and rsp, imm8`, `cli/sti/hlt/pause/mfence`, `movabs r64,
imm64`. ~350–400 строк. Эталоны — байты от GNU `as` (`nix develop`;
`objdump` есть [проба]).

Умножение и деление железом (`imul`, `cdq; idiv`) в шаге 4 не нужны:
рантайм на договоре (шаг 3) перенесёт циклы `rt_mul`/`rt_div` как есть, они
верны на x86. Операции `multiply`/`divide` — отдельное решение после
приёмки (PLAN «Скорость»), иначе байты RV32I изменятся.

## 3. Метки, переходы, раскладка

- **Один проход.** Исполнитель пишет байты в `program.code` по мере эмиссии;
  длина каждой команды известна в момент выпуска; метка — `code.length` при
  `define_label`. Все переходы — `rel32` фиксированной длины, адреса меток
  не зависят от расстояний → двухпроходная раскладка не нужна. Короткие
  `rel8` (−3 байта на переход, ~10–15 % кода) — уборка потом, она и
  потребует двух проходов.
- **Таблица меток** — `layout.Program` (хеш-корзины, `find_label`,
  `label_offset`, `label_address`) как есть: RV в ней нет.
- **Патчи.** В `layout.PatchKind` два нейтральных вида: `REL32` — 4 байта по
  `patch.offset`, значение `цель − (offset + 4)`; `ABS32` — `label_address +
  addend` (адрес гостя). `resolve_patch` получает две ветки по 3 строки
  через `set_section_word` (как `ADDRESS_WORD`). ~25 строк в
  `rv32i/machine/layout`; `emit_patch` переиспользуется. Чистый вынос
  `Program` в `backend/` с разрешением патча у исполнителя — отдельная
  правка; три вида (`REL32`, `ABS32`, `ADDRESS_WORD`) пригодятся и ARM64.
- **Нить `state → layout.Program`** (решение автора — убрать в шаге 4):
  `State.machine = backend.unassigned()`, `use layout` уходит из `state`;
  `executor.new_program` кладёт программу. 65 `state.State {}` в `tr_*`
  получают `machine = layout.Program {}` рядом с уже добавленным `executor =
  rv32i.Executor {}` (или один навык `tr_image.fresh()` — 26 из 65 там).
  Байты RV не меняются: проверка `tests/machine` и ступени.
- **Символы.** `machine.image.symbol_tables` строит `.symtab` для ELF32; для
  ELF64 нужна 24-байтная запись (`Elf64_Sym`) — ~40 строк, и `gdb`/`objdump
  -d` показывают `rt_*`/`saltic_*` по имени (риск 6 отчёта x86).

## 4. Образы, вход, платформа

### Linux — ELF64 (`x86_64_native/image.saltic`, ~150 строк) [предп.]

Из `x86_64_translation/image.saltic` переносятся `Segment`, `append_u32/u64`,
`append_identity`, `append_file_header`, `append_segment` (~70 строк).
`executable(program)` пишется заново — сегменты с `high = GUEST_HIGH`
(0x1_0000_0000 + адрес гостя):

| Сегмент | Адрес гостя | Файл | Права |
|---|---|---|---|
| низкая память | 0 … 65536 | нет | RW (как `layout.host` у RV) |
| код + rodata | 65536 … data_offset | смещение 4096, `image.payload` байт в байт | RX |
| data + bss (арена, куча) | data_offset … memory_size | data | RW |
| строки + страж + стек (8 МиБ, аргументы наверху) | за `align_page(memory_size)` | нет | RW |

`e_entry` = 0x1_0000_0000 + метка `x86_start`. Карта гостя та же, что у
перевода (строки 64 КиБ, страж 1 МиБ, стек 8 МиБ, аргументы 64 КиБ) —
константы `translator` переезжают. Адреса объектов сдвинутся относительно
перевода на разницу длины кода — программы адресов не печатают.

### Linux — вход и вызовы (`x86_64_native/platform.saltic`, ~200 строк)

Смысл готовых байтов [проба, дизассемблер]:

- `ENTRY_*`: `r14 = 0x1_0000_0000`; `rbx = rsp` (стек ядра), `ecx = argc`;
  `[arguments] = argc`; для каждого `argv[i]` (8-байтный указатель
  `[rbx + 8 + 8i]`) — копия байтов до нуля в область строк, 32-битный адрес
  гостя в `[arguments + 4 + 4i]`; `sp гостя = arguments`.
- `SYSCALL_STUB`: `29 → ioctl(16)`, указатель — 3-й аргумент (`rdx += r14`);
  `56 → openat(257)`, `57 → close(3)`, `63 → read(0)`, `64 → write(1)`,
  `93 → exit(60)` — указатель во 2-м (`rsi += r14`), 1-й — `movsxd rdi`
  (−100 у `openat`), 4–6-й — `r10 r8 r9`; прочие → −38. `lseek` (62) и
  `exit_group` (94) в заглушке нет — рантайм их не зовёт [чтение `host`,
  `terminal`].

В родном виде, через кодировщик и с исходником:

- `x86_start`: `movabs r14, 1<<32`; копирование аргументов (~20 команд на
  `rbx rcx rdx rsi rdi r8 r9` — роли ещё не живут); `lea rsp, [r14 +
  arguments]`; `jmp _start`.
- Таблица платформы `SYSCALLS = [номер RV, номер x86, маска указателей]` —
  восемь строк; на каждый — `x86_syscall_<n>`: `push rcx; push r11; movsxd
  rdi, eax; mov esi, edx; mov edx, r8d; …; lea rsi, [r14 + rsi]` (по маске);
  `mov eax, номер; syscall; pop r11; pop rcx; ret`. `x86_syscall_unknown`
  (`mov eax, −38; ret`) — для 500/503 на Linux. Эта таблица — заготовка
  «таблицы платформ» из PLAN (что обязана уметь цель): имя, номер, есть ли.
- `wait` → `pause`, `fence` → `mfence` — в исполнителе.

### UEFI — PE32+ (`x86_64_native/pe.saltic`, ~140 строк)

Из `x86_64_translation/pe.saltic` переносятся заголовки целиком (~100
строк). Своё — `section`/`executable`: одна секция `.text`, **RVA 65536**
(не 4096): тогда `r14 = image_base` ровно, адрес гостя X ↔ RVA X, низкая
память гостя 0…65535 — заголовки и резерв образа (загрузчик выделяет и
обнуляет `SizeOfImage`). Тело в файле — `image.payload` (код + rodata +
data), виртуальный размер — `memory_size − 65536 + строки + стек`; пустая
таблица релокаций 12 байт остаётся. `AddressOfEntryPoint` = RVA метки
`x86_efi_main`. Образ позиционно-независим: переходы `rel32`, адреса гостя
— относительно `r14`.

### UEFI — вход и вызовы (`x86_64_native/uefi.saltic`, ~350 строк)

Смысл готовых байтов [проба]:

- `ENTRY_*`: `push rbx rbp rsi rdi r12 r13 r14 r15`; `r15 = регистровый
  файл`; `[r15+0x100] = SystemTable (rdx)`, `[r15+0x108] = ImageHandle
  (rcx)`, `[r15+0x110] = rsp`; `BootServices->SetWatchdogTimer(0,0,0,0)`
  (`[BootServices + 0x100]`, `BootServices = [SystemTable + 0x60]`) — снимает
  5-минутный сторож прошивки; релокация таблицы переходов (не нужна);
  `r14 = lea(гость) − load_address`; `[r14 + 0] = 1` (argc), `sp гостя =
  stack_top`.
- `SYSCALL_STUB`: `503` (`cpu.call`): `rbx = r14 + a0` — блок в арене
  (`CALL_SCRATCH`, аудит ОС-2): `[rbx] = функция`, `[rbx+0x10…0x58]` — 10
  аргументов по 8 байт, `[rbx+0x60]` — результат; `r12 = rsp; and rsp, −16;
  sub rsp, 0x60`; аргументы 5–10 → `[rsp+0x20…0x48]`, 1–4 → `rcx rdx r8
  r9`; `call [rbx]`; результат в блок и `eax`. `500` (`cpu.firmware`):
  куски 0–3 — `r14`, 4–7 — SystemTable, 8–11 — ImageHandle, по 16 бит.
  `64` (`write`): по байту; `\n` → CR LF, байт ≥ 0x80 → `?`;
  `ConOut->OutputString` (`ConOut = [SystemTable+0x40]`, метод `+8`), буфер
  из двух 16-битных символов. `63` (`read`): `ConIn->ReadKeyStroke` (`ConIn
  = [SystemTable+0x30]`, `+8`); пусто — `BootServices->WaitForEvent(1,
  &ConIn->WaitForKey (+0x10), &idx)` (`+0x60`) и повтор; `UnicodeChar` ≠ 0 →
  байт (≥ 0x80 → `?`), иначе `0x1b`; байт по адресу гостя `a1`, возвращает 1.
  `93` (`exit`): `rsp` из `[r15+0x110]`, `pop` восьми регистров, `xor eax,
  eax; ret` — код выхода всегда 0 (аудит 10.1). `29` → −25, прочее → −38.

В родном виде: те же подпрограммы `x86_syscall_<n>` на кодировщике; вместо
регистрового файла — три слова bss (`saltic_firmware`: SystemTable,
ImageHandle, rsp прошивки) и буфер 16 байт (`saltic_firmware_scratch`).
Вызовы прошивки — из подпрограммы, которая сохраняет летучие регистры-роли
(`rax rcx rdx r8–r11`) на стеке гостя, выравнивает `rsp` на 16 и даёт 32
байта тени. `x86_efi_main`: `push` восьми сохраняемых, `lea r14, [rip − RVA
следующей команды]` (= `image_base`), запись SystemTable/ImageHandle/rsp,
`SetWatchdogTimer(0…)`, `mov dword [r14 + arguments], 1`, `lea rsp, [r14 +
arguments]`, `jmp _start`. `wait` → `hlt`.

Проверка — OVMF (`os/target/uefi_x86_64/run.sh --check` ждёт «Pressed: k.
Bye!»), Acer — последним и только автором (`upload`/`check`).

### Исполнитель как Box и выбор цели

- `x86_64_native.Executor { firmware = no }` — поле, как `far_calls` у RV:
  от него зависят `wait` (`pause`/`hlt`) и обёртка `cli/sti` у `load` в
  `STACK`; подпрограммы `syscall` зовутся по одним меткам — тела выпускает
  платформа при записи.
- `compiler.compile_state_with_options(ast, heap, common, far_calls)` создаёт
  `rv32i.Executor` сам. Нужен навык с параметром `executor`
  (`compile_machine_with_executor(ast, heap, executor)`), `far_calls` уходит
  внутрь `rv32i.Executor { far_calls = yes }` в `compile_machine_far_with_heap`.
  ~15 строк в `compiler.saltic` — новое публичное лицо, решение автора.
- `toolchain.build`: `x86_64-native` / `x86_64-uefi-native` → `@machine =
  compiler.compile_machine_with_executor(tree, heap, x86_64_native.Executor
  { firmware = … })`, затем `x86_64_native.write(path, machine)` /
  `write_uefi` — дописывают платформу в `machine`, зовут `layout.resolve`,
  пишут образ. Повтора «дальние вызовы» у x86 нет (`rel32` на ±2 ГиБ).
- Скрипты: `bootstrap/build.sh` (магия `4d5a` для `x86_64-uefi-native`),
  `tests/run.sh` (хост `x86_64-native` — запуск прямо на процессоре),
  `workbench/same.sh` (третья цель), `workbench/hosts.sh` (ступень
  `x86_64-native all`), новый `workbench/oracle.sh` «перевод против родного».

## 6. Риски и решения для автора

1. **Имена целей** (решено): `x86_64-native`, `x86_64-uefi-native` на время
   перехода; после зелёного `hosts.sh` родной забирает `x86_64`/`x86_64-uefi`.
   Предлагаю переводу на оставшийся релиз имена `x86_64-translation` /
   `x86_64-uefi-translation` — их зовёт `oracle.sh`, паспорта полки
   переименовываются один раз.
2. **`RETURN` без регистра, родные `call`/`ret`.** Быстро (предсказатель
   возвратов), держится на дисциплине «стек на месте перед `ret`» и на том,
   что `RETURN` нигде не значение. Альтернатива — `RETURN` в регистре и `jmp`
   через него (медленнее, лишний регистр). Рекомендую родные; шагу 3 —
   записать в шапку договора: «`RETURN` можно только сохранять в кадр и
   восстанавливать перед `ret`».
3. **Бюджет регистров — 14; роли сверх — в памяти.** Исполнитель не
   заставляет шаг 3 ужиматься до 14, но память медленнее на 1–3 команды за
   обращение. Рекомендую шагу 3 целиться в 14 из таблицы §1 (без
   `ARG4…7`, `SCRATCH6`, `ESCAPE_BOTTOM`, `ARGV`), а `ARGV` убрать из
   договора (ноль обращений в рантайме).
4. **`load` в `STACK` на UEFI.** `mov esp, [m]; add rsp, r14` — одна
   команда с негодным `rsp`; прерывание таймера прошивки в это окно роняет
   машину. Обёртка `cli … sti` только при `firmware = yes` (на Linux `cli`
   запрещён, но прерываний на стек нет). Альтернатива — запасной регистр у
   исполнителя (13 ролей). Рекомендую `cli/sti`.
5. **`wait()` на Linux.** Сейчас — Illegal instruction. Предлагаю `pause`
   (мгновенный возврат); честнее — `nanosleep` через таблицу платформы.
   Решает автор.
6. **Код выхода UEFI всегда 0** (как сейчас). Можно возвращать код как
   `EFI_STATUS` из `efi_main`; агент ОС, возможно, на 0 рассчитывает —
   оставить, пока ОС не попросит.
7. **`_start`: `add(ESCAPE_BOTTOM, HEAP_TOP, ESCAPE_BOTTOM)`.** Если
   `ESCAPE_BOTTOM` окажется в памяти — исполнитель справится через
   `push/pop`, но дешевле переписать `_start` через `SCRATCH0` — 2 строки в
   `state` (байты RV те же? нет: `add s2, s1, s2` → `add t0, s1, s2; mv s2,
   t0` — одно лишнее слово; делать только если роль действительно в памяти).
8. **Патчи в `layout` под `rv32i/`.** Два нейтральных вида в чужой папке —
   компромисс; вынос `Program` в `backend/` — отдельная правка после шага 3
   (нить `state` к тому времени уже убрана).
9. **Адреса кучи отличаются от перевода** (код x86 другой длины): оракулы по
   stdout этого не видят; «куча гостя одинакова» из отчёта x86 (§3 п. 3)
   верно только между родным Linux и родным UEFI.
10. **Готовые байты UEFI восстановлены по дизассемблеру**, не по исходнику;
    смещения служб (`SetWatchdogTimer` +0x100, `WaitForEvent` +0x60,
    `OutputString` +8, `ReadKeyStroke` +8, `WaitForKey` +0x10, `ConOut`
    +0x40, `ConIn` +0x30, `BootServices` +0x60) сверены со спецификацией
    UEFI по памяти [предп.] — при написании `uefi.saltic` сверить с
    `os/target/uefi_x86_64/platform/uefi.saltic`, где те же таблицы на
    Saltic. Порядок проверки — OVMF, потом Acer (решено).
11. **Шаг 3 ещё идёт.** Если договор изменится (имена операций, сжатие
    ролей), меняются только `REGISTER_OF_ROLE`/`ROLE_SLOTS` и список
    методов — остальной план от числа ролей не зависит.
12. **Открытое из PLAN — таблица платформ.** Таблица `SYSCALLS` Linux и
    список подпрограмм UEFI (§4) — готовый черновик: «цель обязана уметь
    write, exit; read, ioctl, openat, close — или честно отвечать −38/−25».
