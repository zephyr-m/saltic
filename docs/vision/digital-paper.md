# Digital paper

S — язык цифровой бумаги.

Цифровая бумага — это единая запись, которую можно читать, проверять, исполнять, объяснять, сохранять и переносить между частями личной вычислительной среды.

Целевая картина готовой системы описана в [Ideal system](ideal-system.md).

S не должен становиться просто ещё одним языком программирования. Его цель — быть общей нотацией для всей экосистемы:

- заметок и планов;
- данных и состояний;
- действий и автоматизаций;
- агентов и роботов;
- программ и инструментов;
- движков, игр, студий и миров;
- runtime, системного слоя и собственного железа.

## Главная цель

Одна экосистема должна говорить на одном языке.

Если объект можно описать, проверить, выполнить или объяснить, он должен иметь форму на S или рядом с S.

```text
paper -> check -> explain -> run -> observe -> modify -> persist
```

## Что значит "удобный S"

S удобен, если его удобно читать человеку и безопасно генерировать агенту.

Это не значит много синтаксиса.

Это значит:

- мало способов сделать одно и то же;
- явные входы и выходы;
- проверяемые ошибки;
- стабильный стиль;
- машинные diagnostics;
- понятное объяснение программы;
- воспроизводимый запуск;
- код, который можно открыть через год и понять.

## Закон читаемости

S должен читаться как проверяемый лист, а не как инструкция компьютеру.

Если новая возможность ухудшает скольжение глаза по тексту, она не принимается без сильной причины.

Реальные tasks являются главным тестом читаемости. Если task становится правильнее, но его тяжелее читать, форма возможности ещё не найдена.

## Базовые понятия

Минимальная ось языка:

```text
data
skill
program
world
agent
runtime
```

`data` описывает состояние.

`skill` описывает переиспользуемое действие.

`program` описывает вход в исполнимый лист цифровой бумаги.

`world` описывает среду, в которой есть состояние, наблюдение и изменение.

`agent` пишет, проверяет, чинит, исполняет и объясняет S.

`runtime` делает цифровую бумагу живой на конкретной машине.

## Критерий новой возможности

Новая возможность нужна только если она помогает хотя бы одному из действий:

- описать реальность точнее;
- проверить программу строже;
- исполнить действие воспроизводимо;
- объяснить результат понятнее;
- убрать ручное соглашение;
- удалить временный слой;
- уменьшить вероятность ошибки агента или человека.

Если возможность просто делает S похожим на обычный язык, она не является целью.

## Критерий удаления

Конструкция должна уйти, если:

- у неё есть два равнозначных способа сделать то же самое;
- она нужна только bootstrap-слою;
- она мешает агентам чинить код автоматически;
- она не появляется в реальных программах;
- она делает цифровую бумагу менее читаемой.

S развивается не через накопление фич, а через уточнение формы цифровой бумаги.

## Текущий практический фокус

Сейчас S должен стать:

- runnable — файл можно выполнить;
- checkable — файл можно проверить;
- explainable — файл можно объяснить человеку и агенту;
- repairable — diagnostics достаточно структурированы, чтобы агент мог исправлять код;
- portable — программа не зависит от случайного bootstrap API.

Поэтому `std`, `check --json`, `explain`, canonical examples и разделение `user/bootstrap` — не отдельные мелочи, а первые слои цифровой бумаги.
