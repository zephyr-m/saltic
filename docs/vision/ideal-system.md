# Ideal system

Этот документ описывает, как S должен ощущаться, когда язык, runtime, ОС, агенты, студия и железо уже готовы.

Это не спецификация текущей реализации. Это целевая картина, против которой проверяются решения.

## Главное ощущение

Ты не работаешь с компьютером как с набором окон, файлов, настроек и команд.

Ты работаешь с живой мастерской цифровой бумаги.

S превращает компьютер в велосипед для ума: мысль быстро становится проверяемой моделью, симуляцией, действием и наблюдаемым результатом.

```text
thought -> model -> check -> simulate -> act -> observe -> correct
```

## Рабочая поверхность

Основной интерфейс — S Studio.

Это не обычная IDE. Это рабочая поверхность, где один лист может быть одновременно:

- документом;
- моделью;
- программой;
- симуляцией;
- интерфейсом;
- журналом решений;
- частью мира.

На верхнем уровне ты видишь не “проект с файлами”, а области реальности:

```text
Дом
Финансы
Роботы
Игры
Движки
Студии
Система
Железо
Миры
Лаборатория
```

Каждая область состоит из цифровых листов. Лист можно читать, проверять, запускать, объяснять, симулировать и применять.

## Работа через намерение

Ты не обязан сразу писать правильный код.

Ты формулируешь намерение:

```text
Хочу модель домашней энергосистемы:
солнечные панели, аккумулятор, потребление, тарифы и аварийный режим.
Покажи, когда система уходит в минус по энергии.
```

Агент создаёт S-лист.

S checker проверяет форму.

S explain показывает смысл.

S runtime запускает симуляцию.

Ты смотришь не только код, а модель:

```text
Модель:
- аккумулятор: 12 kWh
- источник: солнечная панель
- потребители: дом, сервер, зарядка робота

Процессы:
- заряд днём
- расход ночью
- аварийное отключение при 10%

Риски:
- при пасмурной погоде 3 дня подряд батарея падает до 8%
```

Код S остаётся рядом и всегда доступен, но не является единственным интерфейсом.

## Ветки реальности

Любая модель может иметь варианты.

Ты спрашиваешь:

```text
А что если добавить второй аккумулятор?
```

Система создаёт ветки:

```text
baseline
variant/add-second-battery
variant/reduce-night-load
variant/bigger-panel
```

И сравнивает последствия:

```text
baseline: сбой на 3-й день
second battery: стабильно 7 дней
reduce load: стабильно 4 дня
bigger panel: стабильно только при солнце
```

S становится языком проверяемого “а что если”.

## От модели к действию

Когда модель проверена, она может стать действием в реальном мире.

Например:

```text
Если батарея ниже 15%, выключить второстепенные нагрузки.
```

Система показывает, что будет затронуто:

```text
Будет затронуто:
- свет в мастерской
- второй сервер
- зарядка робота

Не будет затронуто:
- холодильник
- сеть
- основной компьютер
```

Только после этого действие применяется.

Важный принцип: действие должно быть объяснимым до исполнения и наблюдаемым после исполнения.

## Один язык для разных миров

Финансы, робот, игра, движок, ОС-сервис и физическое устройство не являются разными вселенными.

Они описываются одной формой:

```text
state
rules
actions
constraints
observations
history
```

Примеры:

```text
world FamilyFinance
objects: account, debt, income, rent
rules: due dates, interest, priority
actions: pay, receive, reserve
```

```text
world WorkshopRobot
objects: arm, camera, table, tool
rules: reach, safety, collision
actions: scan, grab, move
```

```text
world GameWorld
objects: player, door, key, enemy
rules: gravity, collision, inventory
actions: move, pick, open
```

S должен дать один способ думать о разных системах: состояние, ограничение, действие, наблюдение, история.

## ОС как цифровая бумага

ОС тоже описывается листами S.

Не настройки в двадцати местах, а проверяемые правила:

```text
Серверу финансов нельзя иметь доступ к камере.
Агенту сборки можно писать только в build/.
Роботу нельзя двигаться, если человек в опасной зоне.
```

Система должна уметь ответить:

```text
Что это правило защищает?
Кто его может изменить?
Какие действия оно блокирует?
Что случится, если его отключить?
```

## История причинности

Каждое действие сохраняет причинную цепочку:

```text
Что хотел сделать?
Что система поняла?
Какой S-код был создан?
Что сказал checker?
Что объяснил explain?
Что запустилось?
Что изменилось в мире?
Как откатить?
```

Компьютер не должен быть чёрной дырой действий. Он должен хранить причины, последствия и путь назад.

## День из будущего

Пример рабочего цикла:

```text
Ты: Сделай модель расходов на месяц с долгами и вариантами досрочного погашения.

Агент: Создал модель. Нашёл 3 сценария.

Ты: Покажи самый безопасный.

Агент: Вот план. Риск кассового разрыва 12%.

Ты: Почему?

Агент: 24 числа аренда и платёж по кредиту пересекаются с низким остатком.

Ты: Перенеси часть резерва.

Агент: Обновил. Риск 3%.

Ты: Зафиксируй как правило на июль.
```

Под капотом это S:

```text
paper -> model -> check -> explain -> simulate -> act -> observe -> history
```

## Критерий верного направления

S идёт в верном направлении, если каждая новая работа приближает хотя бы одно свойство:

- мысль быстрее становится моделью;
- модель легче проверить;
- действие можно объяснить до запуска;
- результат можно наблюдать после запуска;
- систему можно откатить;
- агенту проще чинить ошибку;
- человеку проще понять лист через год;
- меньше ручной возни с клавишами, файлами и случайными интерфейсами.

Если изменение делает S просто похожим на обычный язык или обычную IDE, это не прогресс само по себе.
