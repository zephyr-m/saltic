# Saltic Code Architecture

Канон организации исходного кода для людей и агентов.

Статус: обязателен.

Версия: 1.

## Назначение

Этот документ отвечает на один вопрос:

> Куда положить следующую строку кода, чтобы проект оставался понятным при росте от
> одной тысячи до десяти миллионов строк?

Правила применяются к любому типу программного обеспечения на Saltic: компилятору,
рантайму, операционной среде, драйверам, SDK, инструментам, играм и пользовательским
программам.

Это архитектура размещения и ответственности кода. Она не определяет модель памяти,
доставку событий, потоки, рендеринг или способ исполнения программы. Документы о
runtime-архитектуре не заменяют этот канон.

Если агент не может однозначно определить владельца кода или место нового модуля,
он обязан остановиться и спросить автора. Придумывать новую форму запрещено.

## Главная идея

Любая кодовая база — дерево модулей.

Каждый модуль имеет одну и ту же форму независимо от размера. Маленький проект —
маленькое дерево. Большой проект — то же дерево с большей глубиной. При росте форма
не меняется и переезд на другую архитектуру не требуется.

Модуль — минимальная архитектурная единица. Файл — только страница внутри модуля,
а не самостоятельный архитектурный слой.

## Физическая форма модуля

Модуль состоит из главного файла и необязательной папки с тем же именем:

```text
compiler.saltic
compiler/
  parser.saltic
  parser/
    lexer.saltic
    grammar.saltic
  checker.saltic
  backend.saltic
  backend/
    rv32i.saltic
```

`compiler.saltic` — публичное лицо модуля `compiler`.

`compiler/` — его внутреннее дерево. Каждый ребёнок снова имеет ту же форму:
`parser.saltic + parser/`, `backend.saltic + backend/` и так далее.

Пустая папка не создаётся. Если у модуля нет детей, достаточно главного файла.

## Ответственность

У каждого модуля ровно одна ответственность, которую можно назвать существительным
или коротким устойчивым понятием: `parser`, `sound`, `storage`, `renderer`, `colony`.

Хорошая ответственность отвечает на вопросы:

- чем владеет модуль;
- какую возможность он предоставляет;
- по какой одной причине он изменяется.

Если части кода имеют разные причины изменения, это разные модули.

Названия `utils`, `common`, `helpers`, `misc` и безымянный `shared` запрещены. Они
скрывают отсутствие владельца. Общий код обязан называться по предоставляемой
возможности: `geometry`, `text`, `collections`, `protocol`, `testing`.

## Публичное лицо и внутренности

Главный файл модуля:

- объявляет или собирает его публичные типы и операции;
- подключает непосредственных детей;
- скрывает устройство внутреннего дерева;
- остаётся стабильным при рефакторинге внутренностей.

Внешний модуль не обращается напрямую к внутреннему файлу чужого модуля. Он зависит
только от публичного лица владельца.

Внутреннюю реализацию разрешено свободно менять, пока публичная поверхность модуля
сохраняет смысл.

Любой исходный код имеет ровно одного владельца-модуль. Файлов без владельца быть
не должно.

## Обязательные лимиты версии 1

- Не более 500 строк кода на один рукописный исходный файл.
- Не более 8 непосредственных дочерних модулей у одного модуля.
- Не более 2000 строк собственного кода модуля без учёта кода потомков.
- Не более 12 публичных операций и типов у одного модуля.
- Не более одной ответственности на модуль.

Пустые строки и комментарии не считаются строками кода. Сгенерированные файлы не
подчиняются лимиту строк, но обязаны лежать в явно названной области `generated` и
никогда не редактируются вручную.

Лимит не обходят длинными строками, бессмысленными прокси-файлами или механической
нарезкой. Превышение означает, что внутри владельца появилась новая ответственность.

Числа меняет только автор архитектуры после проверки на реальном коде.

## Когда создавать ребёнка

Новый дочерний модуль создаётся, если выполняется хотя бы одно условие:

- существующий файл или модуль превышает лимит;
- часть кода имеет отдельное точное имя и собственную ответственность;
- часть кода имеет собственные данные, правила или тесты;
- часть кода изменяется независимо от остального владельца;
- публичная поверхность владельца раздувается из-за отдельной возможности;
- код нужен нескольким частям одного владельца.

Модуль не создаётся только ради уменьшения числа строк. Граница проходит по смыслу,
владению и причине изменения.

При выделении ребёнка внешний интерфейс родителя не обязан меняться. Родитель может
продолжить предоставлять прежнюю возможность, собирая её из детей.

## Минимальная область кода

Новый код всегда начинает жизнь в минимальной области, которой он действительно
нужен.

```text
локальный код
    ↓
внутренний дочерний модуль
    ↓
библиотека ближайшего общего родителя
    ↓
публичный SDK
```

Код не поднимают выше ради предполагаемого будущего использования.

Повторение само по себе ещё не требует общей абстракции. Вынос разрешён, когда у
повторяющегося кода появился общий смысл и стабильная ответственность.

Если одна возможность нужна нескольким модулям, она размещается у их ближайшего
общего владельца. Глобальная библиотека не создаётся, пока потребители принадлежат
одной локальной ветке дерева.

## Роли кода

### Приложение

Поведение конкретной игры или программы остаётся в приложении независимо от объёма.
Большой размер не превращает продуктовую логику в SDK.

### Внутренняя библиотека

Самостоятельная возможность, используемая несколькими детьми одного владельца.
Живёт внутри ближайшего общего родителя и недоступна остальной экосистеме без
отдельного решения.

### SDK

Официальная возможность для авторов независимых программ. Код переносится в SDK,
когда у него есть несколько независимых потребителей либо автор заранее утвердил
его как часть платформенного API. SDK документируется, тестируется и сохраняет
стабильный публичный смысл.

SDK не является складом потенциально полезных функций.

### Runtime

Код, необходимый для исполнения семантики Saltic-программ. Runtime не знает о
конкретных приложениях, UI или инструментах разработки.

### Compiler

Код чтения, проверки и преобразования Saltic в исполняемое представление. Компилятор
не зависит от IDE или конкретных пользовательских программ.

### Core

Минимальная основа, без которой Saltic физически не существует. Важность кода не
делает его частью core. Core обязан оставаться маленьким и иметь минимальное число
зависимостей.

### Driver или adapter

Перевод между Saltic и конкретным железом, протоколом, форматом или внешней системой.
Драйвер не содержит продуктовых правил.

### Tool

Инструмент сборки, анализа, тестирования, генерации или разработки. Tool использует
публичные возможности системы и не становится скрытой частью runtime.

## Зависимости

- Все зависимости объявляются явно.
- Граф зависимостей не содержит циклов.
- Зависимость направлена к более общей и стабильной возможности.
- Внутренний модуль не зависит от продукта, который его использует.
- Core, runtime и SDK не зависят от приложений.
- Драйвер не зависит от продуктовой логики.
- Соседи используют только публичные лица друг друга.
- Если два модуля начинают зависеть друг от друга, общая ответственность выносится
  к их ближайшему общему владельцу.

Расположение рядом не даёт права обращаться к внутренностям соседа.

## Тесты, документация и ресурсы

Тест принадлежит тому же модулю, что и проверяемое поведение. Структура тестов
повторяет дерево исходного кода либо располагается внутри области владельца.

Документация конкретного модуля живёт рядом с ним. Общесистемная документация живёт
у корня системы.

Ресурсы принадлежат использующему их модулю. Общие ресурсы поднимаются к ближайшему
общему владельцу по тем же правилам, что и код.

Сгенерированный и внешний код изолируется в явно названных областях. Агент не
редактирует его и не использует как образец архитектуры.

## Обязательный алгоритм агента

Перед созданием или переносом кода агент отвечает:

1. Какая ответственность добавляется?
2. Какой существующий модуль ею владеет?
3. Можно ли оставить код внутри его текущего файла без нарушения лимитов?
4. Если нужен ребёнок, кто его ближайший родитель?
5. Код локален для одного продукта или является самостоятельной возможностью?
6. Есть ли реальные независимые потребители для переноса в SDK?
7. Относится ли код к исполнению языка, компиляции, железу или инструментам?
8. Не создаёт ли новая зависимость цикл или обратную зависимость?
9. Не обращается ли код к внутреннему файлу чужого модуля?
10. Сохранилось ли небольшое и понятное публичное лицо владельца?

Если нельзя уверенно ответить на вопросы 1, 2 или 4, агент ничего не создаёт и
обращается к автору.

## Запрещённые действия агента

- Создавать новую корневую папку без архитектурного решения автора.
- Складывать код в `utils`, `common`, `helpers`, `misc` или безымянный `shared`.
- Выносить код в SDK на основании возможного будущего использования.
- Делить файл только ради формального прохождения лимита.
- Обращаться к внутренностям чужого модуля.
- Создавать циклическую зависимость.
- Смешивать продуктовую логику с драйвером, runtime, compiler или core.
- Оставлять новый файл без очевидного владельца.
- Создавать параллельную архитектуру ради одной задачи.
- Использовать сгенерированный или архивный код как образец.

## Масштабирование

Проект на тысячу строк:

```text
game.saltic
game/
  world.saltic
  input.saltic
  view.saltic
```

Проект на миллионы строк:

```text
system.saltic
system/
  language.saltic
  language/
    parser.saltic
    checker.saltic
    compiler.saltic
  sdk.saltic
  sdk/
    graphics.saltic
    sound.saltic
    storage.saltic
  os.saltic
  apps.saltic
  tools.saltic
```

Снаружи форма одинакова. Большая система отличается только глубиной дерева и числом
осмысленных ветвей. Каждый отдельный узел остаётся человеческого размера.

## Критерий хорошей структуры

Новый участник или агент должен по пути файла понимать:

- кому принадлежит код;
- зачем он существует;
- является ли он публичным;
- от чего может зависеть;
- куда положить его естественное продолжение.

Если для ответа нужно прочитать половину репозитория, структура нарушена.

Кодовая база считается архитектурно здоровой, когда каждый новый фрагмент получает
минимального владельца, каждый модуль остаётся небольшим снаружи, а рост происходит
рекурсивно внутрь дерева без смены общей формы.
