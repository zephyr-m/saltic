# Target Machine v0

Этот документ очищает первый набросок железа вокруг идей `Minsky Machine`, `Logos Core`, leaflet-сообщений и swarm fabric.

Статус: рабочая гипотеза, не финальная ISA.

## Главная мысль

Целевая машина S не должна наследовать обычный PC/BIOS/desktop stack.

Она ближе к сети простых акторов:

```text
actor state + inbox -> step -> actor state + outbox
```

Подробнее: [Actor Fabric v0](actor-fabric-v0.md).

Минимальная физическая единица называется актор.

Актор имеет:

- маленькое локальное состояние;
- локальную память;
- входящие сообщения;
- исходящие сообщения;
- общий порядок тактов;
- способность исполнять очень маленький набор действий.

## Что в наброске ценное

Из исходного DeepSeek-наброска стоит сохранить:

- минимализм;
- 64-bit слово как базовый payload;
- очень маленький command field;
- акторную модель вместо монолитного компьютера;
- inbox/outbox как базовую форму взаимодействия;
- message fabric как среду обмена;
- идею leaflet: сообщение как маленький переносимый листок данных;
- отсутствие предустановленных ролей у акторов;
- связь с `drum`: такт как физический порядок исполнения.

Это хорошо совпадает с направлением S:

```text
state
input
transition
observation
history
message
protocol
```

## Что пока нельзя считать каноном

Не фиксировать как окончательное:

- точный размер команды `2 bits`;
- точный размер сообщения `66 bits`;
- только четыре инструкции `NOP/INC/DEC/HALT`;
- EEPROM на 100 bytes;
- конкретные микросхемы;
- отсутствие actor id навсегда;
- Python как следующий шаг;
- идею, что S должен напрямую компилироваться в INC/DEC.

Причина: это полезно как минимальная модель вычисления, но слишком узко как реальная целевая машина для всей экосистемы S.

## Слои

Нужно разделить три слоя, которые в исходном наброске смешаны.

### 1. Computational Core

Это минимальная вычислительная модель.

Пример:

```text
NOP
INC
DEC/JUMP
HALT
```

Она отвечает на вопрос:

```text
может ли актор вычислять?
```

Но она не обязана быть единственной ISA для всего S.

### 2. Actor Hardware

Это физическая единица исполнения.

```text
local state
local memory
clock/drum
inbox
outbox
message decoder
step logic
```

Она отвечает на вопрос:

```text
как одна физическая клетка мира S делает шаг?
```

### 3. Message Protocol

Это формат обмена между акторами.

```text
leaflet = command + payload
```

Он отвечает на вопрос:

```text
как акторы передают причины изменений друг другу?
```

Эти слои нельзя склеивать слишком рано.

## Leaflet v0

Рабочая форма сообщения:

```text
leaflet {
    command
    payload
}
```

Исходный набросок:

```text
command: 2 bits
payload: 64 bits
total: 66 bits
```

Это хорошая идея как смысловая форма.

Но физически `66 bits` неудобны для хранения и транспорта. Для реального backend может понадобиться framing:

```text
72 bits
80 bits
128 bits
command word + payload word
```

Пока канон такой:

```text
leaflet = typed command + fixed-size payload
```

Точный packing не зафиксирован.

## Команды v0

Минимальный набор для самого нижнего прототипа:

```text
NOP   ничего не делать
INC   увеличить значение
DEC   уменьшить значение и выполнить условный переход
HALT  остановить актор
```

Открытый вопрос:

```text
DEC должен прыгать когда значение было ноль или когда значение стало не ноль?
```

В классических минимальных машинах обычно нужна ясная форма условного перехода, иначе программы становятся плохо читаемыми.

До фиксации VM/ISA нельзя считать `DEC` окончательным.

## Связь с S

S не должен напрямую зависеть от четырёх команд.

Правильная цепочка:

```text
S source
-> S Machine
-> actor/message effects
-> hardware backend
```

То есть `NOP/INC/DEC/HALT` могут быть нижним substrate, но пользовательский язык не должен думать этими командами.

S должен думать так:

```text
Box        форма состояния
skill      правило перехода
input      причина
visual     наблюдение
world      состояние мира
leaflet    физическое сообщение
actor      исполнитель шага
```

## Влияние на VM

Перед настоящей VM нужно зафиксировать `S Machine`, а не сразу писать bytecode engine.

Минимальная S Machine должна учитывать:

- values;
- frames;
- calls;
- local state;
- effects;
- protocol calls;
- message emission;
- deterministic steps;
- trace/history.

Затем backend может выбрать:

```text
Racket bootstrap
bytecode VM
actor fabric simulation
future hardware
```

## Влияние на visual protocol

`visual.*` не должен становиться HTML API.

Для целевой машины это должен быть protocol output:

```text
S scene -> visual trace -> display leaflet/protocol -> backend
```

Текущий `visual trace` уже совпадает с этой идеей.

## Влияние на time

Акторная машина хорошо совпадает с моделью времени S:

```text
world drum
actor local rhythm
inbox at moment
step
outbox after moment
history
```

Поэтому время не должно быть библиотечной функцией.

Оно должно стать свойством среды исполнения.

## Практический вывод

Этот hardware-набросок полезен не как финальная ISA, а как ограничитель архитектуры:

- не привязывать S к браузеру;
- не привязывать S к обычной ОС;
- проектировать протоколы раньше backend;
- держать runtime маленьким;
- отделять язык от физического packing;
- не строить VM без machine contract.

Actor Fabric фиксирует социальную модель вычисления отдельно: [Actor Fabric v0](actor-fabric-v0.md).

## Следующие вопросы

Перед реализацией VM нужно ответить:

- актор исполняет программу из памяти или реагирует только на leaflets?
- есть ли у актора стабильный identity?
- как адресуется inbox/outbox?
- как выглядит минимальный memory address?
- нужен ли отдельный instruction memory и data memory?
- как message fabric решает конфликт одновременных сообщений?
- есть ли глобальный drum или только локальные ритмы?
- как visual/display protocol попадает из actor fabric в пиксели?
- какой самый маленький useful demo на actor fabric?

## Ближайший правильный шаг

Не писать полноценную VM.

Сначала зафиксировать:

```text
S Machine v0
```

Она должна описать, как S-программа превращается в шаги, effects и trace.

Потом можно сделать:

```text
actor fabric simulator v0
```

И только после этого решать, нужна ли настоящая bytecode VM.
