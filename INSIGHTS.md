# Инсайты

## Три оси вычисления

Если отбросить ввод и вывод, Brainfuck держится на трёх парах действий:

```text
+ / -    данные
> / <    пространство внимания
[ / ]    управление и повторение
```

Три типа вершин графовой машины можно понимать не как инструкции, а как три
вида вычислительной материи:

```text
γ    структура и маршруты
δ    копирование и распространение массы
ε    отсутствие, завершение и стирание
```

Три типа дают шесть локальных отношений. Вычисление находится именно в этих
отношениях: структура сокращается и перестраивается, проходит через
копирование и разрастается, а ненужные ветви исчезают.

Прямого соответствия «одна команда Brainfuck = одно взаимодействие» нет.
Лента, указатель и программа кодируются общей геометрией, а одна команда
становится фрагментом графа и цепочкой локальных взаимодействий.

Условие также становится геометрией: ноль и неноль имеют разные формы, поэтому
при встрече с одним потребителем сами создают разные активные пары. Внешний
проверяющий или глобальный счётчик команд не нужен.

```text
Brainfuck: три пары команд меняют данные, пространство и ход управления.
Граф:      три типа материи через шесть отношений создают вычисление.
```

## Инверсия Brainfuck

Обычный Brainfuck — активная последовательность команд, которая двигает
указатель и изменяет пассивную ленту. Его можно вывернуть:

```text
программа становится неподвижной геометрией;
данные и управление движутся по ней;
локальные встречи изменяют счётчики и связи.
```

После такой инверсии часть команд перестаёт быть командами:

```text
> / <    направление проводов
[ / ]    развилка и обратная связь графа
+ / -    локальное взаимодействие со счётчиком
```

Например, `[->+<]` становится циклическим маршрутом: `DEC` счётчика A при
нуле ведёт к выходу, при ненуле — к `INC` счётчика B, откуда провод возвращает
активность к A.

Внешний instruction pointer исчезает. Его роль выполняет движущийся стикер или
активная пара. Программа больше не читается по порядку — она проходится
физически.

Возможный mapping следует искать не между отдельными командами и парами
агентов, а между составляющими машины:

```text
данные Brainfuck      ↔ локальное состояние агента
движение указателя    ↔ топология портов и проводов
скобки и управление   ↔ активность, развилки и обратные связи
```

После инверсии три оси выглядят как состояние, геометрия и взаимодействие.

## Вычисляет петля, а не счётчик

Один счётчик — только память. Один стикер — только импульс. Один провод — только
направление. Вычисление появляется, когда они образуют замкнутую причинную
петлю:

```text
состояние → стикер → сосед → новый стикер → новое состояние
```

Простейший пример — перенос единичной массы из A в B:

```text
DEC приходит в A

A ненулевой: A уменьшается и отправляет INC в B
B увеличивается и отправляет DEC обратно в A
A нулевой: отправляется HALT
```

При `A=5` и `B=3` ни один участник не знает операции сложения или результата.
Однако повторяющееся взаимодействие заканчивается состоянием `A=0`, `B=8`.

Совместно возникают четыре необходимые составляющие:

```text
состояние       значения счётчиков
изменение       INC / DEC
условие         zero / nonzero
повторение      обратная связь стикера
```

Вычислительная способность принадлежит не отдельному элементу, а устойчивой
цепочке причин между элементами.

## Три скрытые формы и восемь форм Saltic

Saltic не должен программировать фундаментальное графовое ядро напрямую.
Вертикальный контракт разделён на два уровня:

```text
Saltic
  ↓ знает только
8 удобных и стабильных форм языка
  ↓ каждая собрана из
APPLY / DUP / DROP
  ↓ исполняются через
неизменные взаимодействия Logos
```

Три фундаментальные формы скрыты внутри графового слоя:

```text
APPLY    состыковать формы и запустить взаимодействие
DUP      явно организовать совместное использование или размножение
DROP     завершить и поглотить ненужную ветвь
```

Восемь форм являются графовым ABI Saltic. Они могут быть конечными,
циклическими или рекурсивными композициями трёх фундаментальных форм. Saltic
работает только с их стабильными интерфейсами и не зависит от внутренней
геометрии.

Оптимизация внутренней реализации формы не меняет язык, программу или физику
Logos. Добавление удобной формы также не добавляет аппаратный opcode, если она
полностью раскрывается через `APPLY / DUP / DROP`.

```text
3 формы    минимальность и неизменность фундамента
8 форм    выразительность и удобство Saltic
синтаксис человеческое представление программы
```

Это пока архитектурная гипотеза. Её проверка — выразить восемь форм и несколько
разных программ, не добавляя четвёртого фундаментального действия.

## Формулы восьми форм Saltic

Нотация скрытого графового ядра:

```text
APPLY(f, x)       применить форму f к x
DUP(x) → x₁, x₂  дать два явных доступа к x
DROP(x)           поглотить x
WIRE(x) → x       обычное соединение портов, не действие
```

### VALUE

Значение является замкнутой начальной геометрией программы:

```text
TRUE(t, f)  = DROP(f); t
FALSE(t, f) = DROP(t); f

ZERO(f, x) = DROP(f); x
ONE(f, x)  = APPLY(f, x)
TWO(f, x)  = APPLY(f, APPLY(f, x))
N(f, x)    = APPLY f к x ровно N раз
```

### BIND

Количество использований имени становится явной геометрией ресурсов:

```text
BIND(x, 0 uses) = DROP(x)
BIND(x, 1 use)  = WIRE(x)
BIND(x, 2 uses) = DUP(x)
BIND(x, N uses) = дерево DUP с N выходами
```

### CALL

```text
CALL(f, x)       = APPLY(f, x)
CALL(f, a, b)    = APPLY(APPLY(f, a), b)
CALL(f, a...n)   = последовательное APPLY аргументов
```

### SEQUENCE

Чистый неиспользуемый результат поглощается:

```text
SEQUENCE(a, b) = DROP(result(a)); b
```

Для эффектов порядок задаётся обычным причинным значением:

```text
a(token₀) → token₁
b(token₁) → token₂
```

### PAIR

Пара хранит два значения и ожидает потребителя:

```text
PAIR(a, b, k) = APPLY(APPLY(k, a), b)
```

### MATCH

```text
MATCH(pair, handler) = APPLY(pair, handler)

FIRST(a, b)  = DROP(b); a
SECOND(a, b) = DROP(a); b

MATCH(PAIR(x, y), FIRST)  → x
MATCH(PAIR(x, y), SECOND) → y
```

### CHOOSE

```text
CHOOSE(condition, yes, no)
    = APPLY(APPLY(condition, yes), no)

CHOOSE(TRUE, yes, no)  → yes
CHOOSE(FALSE, yes, no) → no
```

Невыбранная ветвь поглощается через `DROP` внутри булевой формы.

### FEEDBACK

```text
FEEDBACK(f) = f(FEEDBACK(f))
```

Физически это конечный граф с обратной связью, а не бесконечная текстовая
развёртка. Повторное использование формы должно проходить через явный `DUP`.

### Статус

```text
VALUE / BIND / CALL / SEQUENCE / PAIR / MATCH / CHOOSE / FEEDBACK
                         ↓
                 WIRE / APPLY / DUP / DROP
```

Это формулы интерфейсов, а не доказательство реализации. Следующая проверка —
определить физические графы и локальные законы `APPLY / DUP / DROP`, не пряча
внутри `APPLY` универсальный интерпретатор.

## Восемь геометрий как исполнитель Saltic

Восемь публичных форм являются пространственной ISA и виртуальным исполнителем
Saltic. Это не opcode: каждая операция языка материализуется как геометрия с
входными и выходными интерфейсами.

```text
Saltic создаёт и соединяет формы
→ активность входит в граф
→ взаимодействия проходят через геометрию
→ на выходе остаётся форма результата
```

Прямой mapping языка:

```text
литерал или функция             VALUE
имя, let, использование         BIND
вызов функции или оператор      CALL
блок и причинный порядок        SEQUENCE
аргументы и составные значения  PAIR
распаковка и pattern matching   MATCH
if и выбор ветви                CHOOSE
цикл и рекурсия                 FEEDBACK
```

Пример `5 + 3`:

```text
CALL(
    VALUE(ADD_FORM),
    PAIR(
        VALUE(5),
        VALUE(3)
    )
)
```

`ADD_FORM` не является девятым opcode. Это именованная библиотечная геометрия,
сама выраженная композициями тех же восьми форм.

Уровни не следует смешивать:

```text
Saltic
  ↓ прямой mapping
8 публичных геометрий — пространственный исполнитель языка
  ↓ внутренняя реализация
APPLY / DUP / DROP
  ↓ физика
неизменные Logos
```

Сначала проверяется полнота mapping `Saltic → 8 форм`. Только затем исследуется
реализация восьми форм через три скрытые формы и Logos.
