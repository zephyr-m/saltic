# Actor Fabric v0

Этот документ фиксирует целевую модель вычисления для будущей аппаратной среды S.

Статус: рабочий канон направления, не финальная реализация.

## Главная мысль

S target machine is an actor fabric.

```text
actor is not a CPU
actor is a participant
computation is interaction over time
```

Вдохновение: люди, социальные взаимодействия, группы, договорённости, сообщения и роли.

Актор — это очень упрощённая версия участника мира.

Он сам является частью вычисления, а не просто исполняет чужую программу.

## Не CPU

Обычная модель:

```text
CPU -> executes program -> changes memory
```

Целевая модель S:

```text
actor receives message -> reacts -> changes local state -> emits messages
```

Вычисление не находится в одном центре.

Вычисление рождается из сети взаимодействий:

```text
many actors + messages + time = computation
```

## Минимальный актор

Актор имеет:

```text
identity
local state
local memory
inbox
outbox
reaction rules
local rhythm
history
```

Минимальная формула:

```text
actor(state, inbox, moment) -> actor(next state, outbox)
```

Это совпадает с моделью S:

```text
Box        форма состояния
input      входящее сообщение
skill      правило реакции
transition переход состояния
outbox     исходящие сообщения
history    наблюдаемая цепочка
```

## Сообщение

Сообщение — единственный способ повлиять на другого актора.

Акторы не лезут в локальную память друг друга.

Рабочее имя сообщения:

```text
leaflet
```

Смысл:

```text
leaflet = маленький переносимый листок причины
```

Минимальная форма:

```text
leaflet {
    command
    payload
}
```

На физическом уровне command может быть очень маленьким, например 4 opcode:

```text
NOP
INC
DEC
HALT
```

Но на уровне S это не должно выглядеть как обычные инструкции CPU.

Это нижний алфавит физического сообщения.

## Социальная аналогия

Актор похож не на процессор, а на участника:

- имеет локальное состояние;
- видит только свои входящие сообщения;
- не знает весь мир напрямую;
- может помнить историю;
- может иметь роль;
- может принять, отклонить, изменить или переслать сообщение;
- может породить новое сообщение;
- действует в общем времени среды и в своём локальном ритме.

Эта аналогия нужна не для поэзии.

Она ограничивает архитектуру:

- не делать глобальную память главным способом общения;
- не делать central scheduler единственным источником смысла;
- не превращать актор в class/object;
- не считать function call моделью общения;
- не проектировать VM как обычный процессор.

## Роль 4 opcode

Пока точно известно:

```text
есть акторы
есть 4 opcode
```

Это достаточно для нижнего слоя, но недостаточно для всей архитектуры.

Канон:

```text
4 opcode = физический алфавит leaflets
actor fabric = вычислительная среда
S Machine = мост от языка к fabric
```

То есть:

```text
S skill
-> reaction rule
-> actor transition
-> emitted leaflets
-> fabric delivery
```

А не:

```text
S source -> INC/DEC program
```

## Время

Actor Fabric существует во времени.

Минимальный цикл среды:

```text
moment begins
deliver pending leaflets
actors inspect inbox
actors react according to local rhythm
actors update local state
actors emit outbox leaflets
fabric records history
moment ends
```

Это ещё не синтаксис S.

Это свойство будущей среды исполнения.

## Local rhythm

У актора может быть локальный ритм относительно времени среды.

```text
local rhythm = local time / environment time
```

Это не отдельная вселенная и не отдельный глобальный clock.

Это скорость внутренней реакции участника относительно общего порядка событий.

## Message Fabric

Message Fabric — это среда доставки сообщений.

Она отвечает за:

- доставку leaflets;
- порядок доставки;
- broadcast;
- конфликт одновременных сообщений;
- историю сообщений;
- наблюдаемость;
- ограничения пропускной способности.

Пока не решено:

- есть ли адреса акторов;
- как выглядит identity;
- как актор появляется;
- как актор исчезает;
- есть ли приватные каналы;
- можно ли отправить leaflet самому себе;
- что происходит при переполнении inbox;
- как задаётся порядок при одновременной доставке.

## Связь с цифровой бумагой

Цифровая бумага в S не должна быть только визуальным холстом.

Она должна быть живым листом, где объекты и агенты являются участниками.

```text
engineering sheet
objects
actors
messages
state
observation
history
```

Живой чертёж оживает не потому, что его перерисовал renderer.

Он оживает потому, что его части могут быть акторами и обмениваться сообщениями.

Дальний север этой модели — programmable matter: акторы становятся клетками материи, а форма становится коллективным состоянием. См. [Programmable Matter](../vision/programmable-matter.md).

## Связь с visual observation

`visual.*` показывает состояние.

Actor Fabric создаёт поведение.

```text
actor interaction -> state/history -> visual observation
```

Поэтому visual protocol не должен становиться главным вычислительным слоем.

Он является наблюдением, а не причиной мира.

## Связь с VM

Если делать VM до Actor Fabric, есть риск получить обычный процессор.

Правильный порядок:

```text
Actor Fabric v0
S Machine v0
runtime contract freeze
bytecode/VM only if needed
hardware backend
```

S Machine должна описывать не только вычисление выражений, но и:

- moment;
- actor step;
- inbox;
- reaction;
- outbox;
- effects;
- trace;
- observation.

Первый контракт S Machine зафиксирован в [S Machine v0](../spec/s-machine-v0.md).

## Не входит в v0

- финальная ISA;
- упаковка leaflets в биты;
- физическая шина;
- scheduler;
- memory layout;
- безопасность;
- распределённый consensus;
- network protocol;
- real-time guarantees;
- routing algorithm;
- экономическая модель акторов.

## Практическое правило

Не добавлять VM-фичу, пока не понятно, как она выглядит в Actor Fabric.

Не добавлять protocol-фичу, пока не понятно, какое взаимодействие акторов она обслуживает.

Не добавлять visual-фичу, пока не понятно, какое состояние или историю она наблюдает.
