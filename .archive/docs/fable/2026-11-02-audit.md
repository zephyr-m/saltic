# Аудит Saltic: согласованность языка и DRY

Дата: 02.11.2026. Аудит провёл агент (Claude Fable) только чтением кода.
Что из этого взято в работу — в `docs/PLAN.md`, решения — за автором.
Срез: HEAD на момент чтения уже содержит «шаг 1» деревьев групп (`KIND_TREE`,
`rt_group_tree_*`); незакоммичены `soul/seed/core/group.saltic` (новый `tree_add`
на Saltic и шапка файла), `docs/PLAN.md`, `tests/groups.saltic`. Дерево менялось
прямо во время аудита, поэтому номера строк — на момент чтения.

Метки: **[чтение]** — проверено чтением кода; **[запуск]** — проверено
пробной программой; **[предп.]** — предположение, не проверено запуском.

## Краткий итог

Ядро идеи — «одну вещь одним способом» — в синтаксисе выдержано хорошо:
одна форма условия, один цикл `drum`, одна модель ошибок `out error.X` /
`rescue`, один список (группа), Box с умолчаниями, `== no` вместо отрицания.
Канон (`soul/canonical`) с ожидаемым выводом и ожидаемыми ошибками — редкая
и очень полезная вещь. Документация (README, FOR-HUMANS, TESTING, PLAN) не
расходится с каноном по синтаксису — я проверила grep'ом на `not`, `<=`,
`else`, `return`, `use seed.` в примерах: расхождений нет.

Где язык *не* один-путёвый, это почти всегда следствие двух известных ограничений,
а не новых решений: 29-битных чисел (половинки hi/lo, `drum (268435455)` как
вечный цикл) и запрета фиксированных типов вне навыка. Это не новости, но
их цена в коде заметна и перечислена ниже.

Главные настоящие несогласованности (часть А): глаголы ядра (`str.add` ≠
`group.add`, `len` ≠ `count`), один `mem.load8` с двумя контрактами по типу
первого аргумента, две записи конверсии (`u8(n)` и `u16.from(x)`), `beat` с
двумя смыслами, значение блока только у `rescue`, запятая в Box как исключение
(уже в PLAN), сообщения парсера мимо `errors.saltic`, коды ошибок,
переиспользуемые для разных ситуаций, часть диагностик без позиции.

Главные повторы (часть Б) в компиляторе: таблицы intrinsic'ов в пяти
параллельных `switch`-ах (одна встроенная операция — 9 правок в 4 файлах),
мёртвый текстовый путь эмиссии (`emit_writable`/`emit_data`/`emit_blank` —
пустышки, но 22 вызова и три `Output` в `State`), фасад `abi.saltic` из
74 констант и 39 однострочных прокси, строковая кодировка типов
`"box:Имя"`/`"group:тип"` с магическими `tail(type, 4|5|6)` в 11 файлах,
разбор чисел и выравнивание, написанные по три раза, и — главное
системное — шапки файлов есть у 22 файлов из ~230 (в `core` — 0 из 21).

Счёт находок: А — 17 (+6 «язык в бою» из кода ОС), Б — 14 (ядро/компилятор,
моё чтение) + 16 (рантайм, ветка 1) + 11 (ОС/UIEngine, ветка 2) = 41.

### Что делать первым (предложение, решает автор)

1. **До заморозки — имена и формы ядра** (А1, А2, А4, А8, А9, А16): это единственное, что потом не поправить. Один вечер решений автора + механические переименования.
2. **Шапки `core/*` и публичных лиц `selfhost`** (Б1) — дёшево, снимает чтение исходников агентами.
3. **Мёртвый текстовый путь эмиссии + мёртвые `rt_add/sub/less/greater`** (Б3 ветки 1) — бинарник не меняется, самосборка это докажет; убирает ловушку.
4. **Именованные смещения нагрузки и ширина дерева в одном месте** (Б2.1, Б2.2 ветки 1) — прямой риск для свежего шага деревьев; плюс контракт T6 (Б5).
5. **Таблица intrinsic'ов** (Б2 основной части) — одна запись на операцию вместо шести `switch`.
6. ОС: константы прошивки в `platform/uefi`+`storage/files` (Б-ОС-4), `files.write_file/delete` (Б-ОС-5), таблица ASCII (Б-ОС-7 — там ошибка данных).

Оговорка о номерах строк: автор правил дерево во время аудита (например,
`state.saltic` сдвинулся на ~20 строк между двумя чтениями), поэтому номера
точны на момент чтения конкретного файла и могут плавать на десяток строк.

## А. Согласованность языка

### А1. `str.add` склеивает, `group.add` добавляет элемент — один глагол, два смысла
- Где: `soul/seed/core/str.saltic:4` (`skill add(left, right) native` — конкатенация двух строк), `soul/seed/core/group.saltic:19` (`skill add(group, value) native` — добавить один элемент), `soul/seed/core/group.saltic:35` (`concat(left, right)` — склейка двух групп).
- Почему: у строк «склеить две» = `add`, у групп «склеить две» = `concat`, а `add` = «положить элемент». Программист, зная `str.add`, ожидает от `group.add([1],[2])` группу `[1,2]`, получает `[1,[2]]`.
- Предложение: один глагол на одну операцию у всех последовательностей: `str.concat`/`group.concat` для склейки и `group.add` (или `push`) для элемента; либо `str.add` переименовать в `str.join2`… Решает автор; но до заморозки это стоит закрыть, потому что имена ядра — часть синтаксиса для пользователя.
- Важность: высокая (замораживается). Цена: переименование + 1 строка в `intrinsic.saltic` + grep по проекту (478 вызовов `str.add`, 318 `group.add`, 34 `group.concat` на 02.11.2026). **[чтение]**
- Проверено запуском: `group.add([1, 2], [3, 4])` → 3 элемента (`[1, 2, [3, 4]]`), `group.concat([1, 2], [3, 4])` → 4. Варианты имени для склейки обсуждались с автором: `glue`, `join` (занят смыслом «через разделитель» в других языках), `concat`, `merge`, `extend`, `chain`. **[запуск]**

### А2. `str.len` и `group.count` — разные слова для «сколько»
- Где: `soul/seed/core/str.saltic:5`, `soul/seed/core/group.saltic:17`; `str.line_count` (`str.saltic:3`) ещё и третье слово.
- Предложение: одно слово (`count` везде или `len` везде). Важность: средняя. Цена: как А1. **[чтение]**
- Проверено запуском: `str.len("привет")` → **12** — считаются байты UTF-8, а не буквы. Значит, `str.len` и `group.count` отвечают на разные вопросы, и честнее имя `str.bytes`; число букв (`str.count`) — отдельный навык, если понадобится. **[запуск]**

### А3. `mem.load8/store8` — одно имя, два контракта по типу первого аргумента
- Где: `soul/canonical/main.saltic:170-176` (`@region = [0, 4096]`, `mem.store8(region, 0, …)` — адрес как группа `[hi, lo]`, смещение число, результат число) и `main.saltic:189-199` (`mem.store8(memory, usize(0), u8(171))` — адрес `address`, смещение `usize`, результат `u8`). Развилка живёт в `soul/seed/selfhost/intrinsic/memory.saltic:21-59` (`load_type`, `target` по `address_type == "address"`).
- Почему: единственное место языка (кроме `drum`), где одно имя значит две операции с разными типами аргументов и результата. Это перегрузка, которой в языке больше нигде нет.
- Предложение: либо честно два имени (`mem.load8` для сырого `[hi, lo]`, `address.load8` для типизированного), либо один контракт после прихода 64-битных чисел (группа `[hi, lo]` исчезнет сама). Важность: средняя; закроется решением о 64 битах. **[чтение]**

### А4. Две записи для получения фиксированного значения: `u8(n)` и `u16.from(x)`
- Где: `soul/canonical/main.saltic:181-185` — `u8(250)`, `u16.from(u8(250))`, `address(u32(8192))`. `u8(...)` нигде не объявлен как навык — это магия по имени типа (`contract.is_fixed_type(name)` в `soul/seed/selfhost/compiler/codegen.saltic:238`, `checker/signatures.saltic:52`), а `u8.from` объявлен в `soul/seed/core/u8.saltic:1`.
- Почему: «число → фиксированное» пишется вызовом типа, «фиксированное → фиксированное» — через `.from`; при этом `address(u32(...))` — снова вызов типа от фиксированного. Три формы на одну идею «привести к типу».
- Предложение: одна форма — либо всегда `T(x)` (и убрать `from`), либо всегда `T.from(x)`. Важность: средняя-высокая (синтаксис). Цена: чекер+кодоген ~30 строк, канон. **[чтение]**

### А5. `beat` — индекс при `drum (число)` и элемент при `drum (группа)`
- Где: `soul/seed/core/str.saltic:78-81` (`drum (group.count(items)) { … group.get(items, beat) }` — индекс) и `soul/seed/core/group.saltic:6-8` (`drum (items) { (beat == value) … }` — элемент). Канон: `main.saltic:120` и `main.saltic:245`.
- Почему: одно слово меняет смысл по типу аргумента; в коде ядра приходится писать `drum (group.count(x))`, чтобы получить индекс, то есть нет способа получить и элемент, и индекс.
- Предложение: автор может считать это осознанным; тогда стоит зафиксировать в каноне явно (в `main.saltic` оба случая есть, но без комментария в шапке). Важность: низкая-средняя. **[чтение]**

### А6. Значение блока существует только у `rescue`
- Где: `soul/canonical/main.saltic:246-249` — последнее выражение блока `rescue |err| { … current }` становится значением; `main.saltic:147-150` — внутри того же блока `out err` выходит из навыка. У `(cond) { }`, `pick`, `drum` значения блока нет; у `(enum) { .X => выражение, }` ветка — выражение с запятой (третья форма).
- Почему: три способа «блок даёт значение»: хвостовое выражение (только `rescue`), `=>` (только сопоставление enum), `out` (навык). Парсер: `parser/syntax.saltic:508` (rescue), `:621-656` (switch), `:662` (if).
- Предложение: до заморозки решить, допускается ли хвостовое выражение в любом блоке (тогда `pick` становится выражением) или только в `rescue` — и записать в шапку канона. Важность: средняя (синтаксис). **[чтение]**

### А7. `(x) { … }` — условие или сопоставление, решает содержимое скобок `{}`
- Где: `parser/syntax.saltic:621-662` — после `(выражение)` парсер смотрит, начинается ли тело с `.ИМЯ =>`, и строит `switch`, иначе `if`.
- Почему: одна внешняя форма, два смысла; читателю нужно заглянуть в тело. Это согласовано с «одной формой условия», но противоречит «одна вещь — один способ» в обратную сторону: два разных действия одной записью.
- Предложение: автор, вероятно, считает это одной вещью («разбор значения»). Тогда просто зафиксировать. Важность: низкая. **[чтение]**

### А8. Запятая: в enum, группах, аргументах, параметрах хвостовая разрешена, в Box запрещена
- Уже в `docs/PLAN.md` («Решает автор»). Подтверждение в коде: исключение зашито в `parser/syntax.saltic:130-134` (`field_comma_message`) и `:169-176` (`item.node.tag == "field"`), все остальные последовательности идут общим `sequence(..., allow_comma = yes)` (`:191, :342, :412`).
- Предложение: убрать особый случай — одна строка `sequence` для всех. Важность: средняя (синтаксис). Цена: ~10 строк парсера + канон ошибок. **[чтение]**

### А9. `io.show` — единственный навык с переменным числом аргументов
- Уже в PLAN. В коде: `soul/seed/io.saltic:1` объявлен как `show(value)` с одним параметром, а `intrinsic.saltic:131-139` даёт ему `minimum 1 / maximum 8`; `codegen.saltic:237` отдельная ветка `compile_show`. Объявление в `io.saltic` врёт о числе параметров. Важность: средняя; цена — решение автора о записи. **[чтение]**

### А10. Сообщения парсера идут мимо `errors.saltic`
- Где: `soul/seed/selfhost/errors.saltic` — 70 именованных диагностик с кодами; `parser/syntax.saltic` — 41 строка с текстом ошибки прямо в вызове `fail(next, "ожидалась (")`, `:95, :180, :196, :223, :234, :263, :265…`, все под одним кодом `parser_error` (`errors.saltic:253`, `unexpected_token`).
- Почему: у чекера одна ошибка = один навык с кодом; у парсера — произвольная строка и общий код. Инструменты (LSP, тесты) не могут отличить «ожидалась )» от «ожидалось имя skill».
- Предложение: парсерные ошибки тоже как навыки в `errors.saltic` (или в `errors/parser.saltic`) с кодами `expected_paren` и т. п. Важность: средняя. Цена: ~40 вызовов, механическая. **[чтение]**

### А11. Один код ошибки на несколько разных ситуаций, и наоборот
- Где: `errors.saltic` — код `type_mismatch` у 6 навыков (`:93, :97, :121, :261, :265` и `argument_type_mismatch`), `duplicate_definition` у 7 (`:17-41`), `operator_type_mismatch` у 5 (`:205-221`), `call_arity` у 3, `module_error` у 2 (`:273, :277`), `parser_error` у всего парсера. При этом `fixed_integer_argument` и `fixed_integer_out_of_range` — отдельные коды на близкие случаи.
- Почему: код либо идентификатор ситуации, либо категория; сейчас — то и другое. Для `expected/errors/*.txt` сверяются и код, и текст, поэтому работает, но для инструментов — нет.
- Предложение: правило «код = имя навыка в errors.saltic» (как уже у 50 из 70). Важность: низкая-средняя. Цена: ~15 строк + `expected/errors/*.txt`. **[чтение]**

### А12. Часть диагностик без позиции (`0|0`)
- Где: `soul/canonical/expected/errors/operators.txt` — `operator_type_mismatch|0|0`; причина — `checker/walk.saltic:108` добавляет ошибку без `lookup.placed(node, …)`, в отличие от соседней строки `:97`. Все `duplicate_definition` (`boxes.txt`, `skills.txt`, `program.txt`, `constants.txt`) — `0|0`: `top_level.saltic:58, :110, :120` тоже без `placed`.
- Предложение: везде через `placed`; для верхнеуровневых — позиция узла есть (`ast.location`). Важность: средняя (удобство каждый день). Цена: ~6 строк + expected. **[чтение]**

### А13. Два механизма для пути `seed.…`: «seed не импортирован» и `long_path`
- Где: `checker/lookup.saltic:78-83` — `name == "seed"` → `seed_not_imported` / `unknown_seed_operation`, `top_level.saltic:27-29` — `__seed__`; текст ошибки советует `use seed` (`errors.saltic:57`). Одновременно канон `soul/canonical/errors/calls.saltic:10-11` → `long_path` с советом `use seed.group`. В каноне ожидаемого вывода `seed_not_imported` не встречается.
- Почему: старый путь (`use seed`) остался в чекере рядом с новым правилом импорта из PLAN «Сейчас». Два совета в двух ошибках противоречат друг другу.
- Предложение: удалить ветку `seed` и `__seed__`. Важность: низкая. Цена: ~15 строк. **[чтение]**, что ветка мёртвая — **[предп.]**

### А14. Сообщение `field_type_mismatch` в двух редакциях
- Где: `errors.saltic:101` («…полю 'x' Box 'Point' типа number») и `:181` (`field_assign_type_mismatch`, без «типа …»); видно в `expected/errors/boxes.txt` и `fields.txt`.
- Предложение: один навык, один текст. Важность: низкая. Цена: 5 строк. **[чтение]**

### А15. Имена ошибок: `OutOfRange` и `OutsideRange`, `Bad*` и `Invalid*`
- Где (grep по `error.[A-Z]…` в seed+os): `PatchOutOfRange` против `ValueOutsideRange`, `WordOutsideRange`, `ByteOutsideRange`, `BufferOutsideRange`; `BadAddress` против `InvalidAddress`; системная `File` (`abi/errors.saltic:9`) против `ReadFailed`/`WriteFailed` в ОС. Также `bits32.not` (`core/bits32.saltic:4`) — единственное `not` в языке, где отрицания нет принципиально (`== no`).
- Предложение: словарик имён ошибок в каноне (одно слово на «вне диапазона», одно на «неверный»); `bits32.not` → `bits32.invert`. Важность: низкая. **[чтение]**

### А16. Максимум числа задан в пяти местах, а «вечный цикл» пишется как `drum (268435455)`
- Где: `abi/value.saltic:16-18` (`NUMBER_MAXIMUM`, `_TEXT`, `_MINIMUM_TEXT`), `abi/errors.saltic:20` (`MAXIMUM_TEXT`), `core/time.saltic:1` (`COUNTER_LAST`), `parser/syntax.saltic:736` (`@limit = "268435455"` — литерал в парсере), `os/drivers/sound.saltic:44`; вечный цикл: `os/main.saltic:42-43` (вложенные `drum (268435455)`), `os/drivers/keyboard.saltic:59`.
- Почему: граница числа — факт ABI, он должен быть в одном месте; «цикл без конца» — идиома, которую язык не выражает, поэтому каждый пишет магическое число (и это ещё и причина утечки регионов из PLAN).
- Предложение: одна константа `abi.NUMBER_MAXIMUM` + решение автора о форме вечного цикла (например, `drum { }` без аргумента) до заморозки. Важность: средняя. **[чтение]**

### А17. Изменяемость: Box по ссылке, но код местами перестраивает группу вокруг изменённого Box
- Где: `selfhost/diagnostic.saltic:30-38` (`in_module`): меняет `item.message` на месте и тут же собирает новую группу из тех же Box — второе лишнее, если Box по ссылке; `compiler/state.saltic:78-83` (`type_set`) — та же пара. Модель (`docs/language/MEMORY-MODEL.md`, «Список побегов») говорит: Box меняется на месте.
- Почему: код показывает неуверенность в правиле; читатель не понимает, копируется ли Box при `group.get`.
- Предложение: зафиксировать в каноне `main.saltic` пример «изменение Box, лежащего в группе, видно через группу» и убрать пересборку. Важность: низкая. **[чтение]**, что пересборка лишняя — **[предп.]** (зависит от семантики `group.get`, которую я по рантайму не проверяла).

### Что сделано хорошо (А)
- Одна форма условия, один цикл, `== no`, `out error.X`/`rescue` — выдержано во всём проекте без исключений, которые я бы нашла grep'ом.
- `str.slice/contains/starts_with` и `group.slice/contains` — одинаковый порядок аргументов. `str.get` → строка, `str.byte` → число — честно разведено.
- Канон с `expected/` — работающий механизм против дрейфа; документация синтаксису не противоречит.
- Сообщения компилятора — единый язык (русский), единый тон (императив «подключи», «назови»), почти везде код = имя ситуации.

## Б. DRY — ядро, компилятор, чекер (моё чтение)

### Б1. Шапка файла — правило канона — есть у 22 файлов из ~230
- Где: `docs/Code_Architecture_канон_для_агентов.md`, раздел «Шапка файла» («Каждый исходный файл начинается с шапки»). Факт: `soul/seed/core` — 0 из 21, `soul/seed/selfhost` — 1 из 63 (`compiler/codegen.saltic`), `os/uiengine` — 0 из 60, `os/drivers` — 0 из 15, `os/target/uefi_x86_64` — 21 из 53. (Незакоммиченный `core/group.saltic` шапку получил.)
- Почему это DRY-вопрос: без шапки агент читает исходник, чтобы узнать контракт, и «знание о модуле» живёт только в головах и в чужих вызовах.
- Предложение: начать с `core/*` (21 файл, по 3–8 строк каждый) и публичных лиц `selfhost` (`parser`, `checker`, `compiler`, `abi`, `intrinsic`, `machine/layout`). Важность: высокая (это канон, он нарушен в 90 %). Цена: ~1 строка на навык, 2–3 часа на `core`+`selfhost` публичные лица. **[чтение]**

### Б2. Одна встроенная операция = 9 правок в 4 файлах (пять параллельных таблиц в `intrinsic.saltic`)
- Где: `soul/seed/selfhost/intrinsic.saltic` — enum `Kind` (`:3-18`), `find` (`:20-68`), `exact_argument_count` (`:70-123`), `result` (`:133-183`), `argument_type` (`:185-229`), `target` (`:231-260`) — шесть списков по ~50 строк, все по одному и тому же ключу. Плюс объявление `native` в `core/x.saltic`, навык `emit_*` в `runtime/emit/*.saltic` и регистрация в `runtime/emit.saltic:17-100`. Проверено на свежем `tree_parts`: затронуты `intrinsic.saltic`, `emit/collections.saltic`, `emit.saltic`, `core/group.saltic`.
- Почему: одна сущность описана шестью `switch`-ами; забыть одну строку легко (чекер молча вернёт `"unknown"`).
- Предложение: одна таблица-группа записей `[имя, минимум, максимум, результат, типы аргументов, метка rt]` и навыки, читающие её; `Kind` остаётся индексом. Язык это позволяет (группы групп). Важность: высокая. Цена: ~150 строк заменить на ~70; полдня, проверка самосборкой. **[чтение]**

### Б3. Мёртвый текстовый путь эмиссии
- Где: `compiler/state.saltic:134-144` — `emit_data`, `emit_writable`, `emit_blank` возвращают `compiler` без действия; при этом 22 вызова живут в `codegen/emitters.saltic` (7), `constants.saltic` (4, в `emit_storage` — строки `"  .word {STATE_EMPTY}"` рядом с настоящим `layout.append_section_word`), `functions.saltic` (2), `state.saltic` (5). `State.lines/data/writable` (`state.saltic:40-42`) и `output_add`/`output_text` (`:103-130`) обслуживают только этот путь; `finish_data` склеивает всегда пустые тексты. Подробнее и с найденным расхождением текста и бинарника — в разделе ветки 1, Б3.
- Почему: это след удалённого ассемблерного вывода; читатель думает, что компилятор пишет два представления, и рискует «починить» только одно.
- Предложение: удалить три пустышки, 22 вызова, три поля `Output` и `output_*`. Важность: средняя. Цена: ~80 строк удалить, час. **[чтение]**

### Б4. `abi.saltic` — фасад из 74 констант и 39 прокси-навыков
- Где: `soul/seed/selfhost/abi.saltic` (245 строк): каждая константа ребёнка переобъявлена (`TAG_NUMBER = tags.NUMBER`…), каждый навык — однострочный `out child.f(x)`. Канон запрещает «бессмысленные прокси-файлы» и ограничивает 12 публичных операций.
- Почему: любое изменение `abi/*` — две правки; 113 публичных имён у одного модуля.
- Предложение: потребители подключают детей напрямую (`use selfhost.abi.tags`) — так уже делают `abi/*` сами и `memory/model.saltic`; `abi.saltic` оставить для действительно общих вещей. Либо, если автор хочет «одно лицо», — это решение автора, но тогда лимит 12 для `abi` надо явно снять. Важность: средняя. **[чтение]**

### Б5. Строковая кодировка типов `"box:Имя"`, `"group:тип"`, `"enum:Имя"` размазана по 11 файлам

- Предложение: `types.box_name(type)`, `types.enum_name(type)`, `types.item_type(type)` и `types.is_box(type)` в одном месте (`checker/types` уже почти оно) и использовать их из кодогена. Важность: средняя. Цена: ~12 замен. **[чтение]**

### Б11. Обход AST переписывается на каждую задачу
- Где: `compiler/state.saltic:138-205` (`collect_*_names`), `:207-300` (`*_uses_beat`), `checker/walk.saltic`, `codegen.saltic` — четыре полных `switch` по тегам `var/assign/field-assign/out/expr/if/pick/switch/drum/rescue`.

### Б3. Двойная эмиссия: текстовый ассемблер мёртв, но не удалён

  `PADDING` объявлен 19 раз (8/10/12/14/16/18), `RADIUS` 18 раз (4/6/8/10/18), `HEIGHT` 16, `GAP` 8 — хотя PLAN заявляет «токены вместо чисел раскладки», а `layout.saltic` уже держит `GAP = 12`.
- Предложение: `shapes.label_box(screen, x, y, width, height, radius, text, face, style, under)` и токены `PAD_SM/MD/LG`, `RADIUS_SM/MD/LG` в `canvas`/`layout`; компоненты оставляют только настоящие отличия.
- Важность: средняя. Цена: 2–3 часа, проверка галереи на Acer.

### Что сделано хорошо (ОС)
- `platform/firmware.saltic` — образцовая шапка-договор и единственная точка вызова прошивки (`call`/`call_wide`); всё остальное идёт через него.
- `storage/files.saltic`, `storage/notes.saltic`, `platform/utf8.saltic` — честные шапки; ошибки `WriteFailed`, `NoSalticVolume`, `BelowGuestBase` читаются как текст.
- Драйверы (`rtl8111`, `qca9377/*`) разложены по детям (bmi/htc/rings/boot) и не лезут в прошивку мимо `firmware`.
- UIEngine: каждая компонента — файл в 15–40 строк с одним `*_width` и одним `draw_*`; форма одинакова у всех 60.

## А (дополнение). Язык в бою — из кода ОС

1. **Цикл «пока» пишется как `drum (большое число)` с `out` внутри** — `drivers/rtl8111.saltic:118` (`drum (100000)` ждёт сброса бита), `tools/snippets/smbios.saltic:23` (`drum (4000)` читает строку до нуля), `programs/pci.saltic:27`, `agent.saltic:560` (`drum (200000000)` — вечный цикл), `storage/disk.saltic:64` (`drum (4)` вместо «пока lo < 0»). `LOOPS/FRAMES/WAITS/POLLS = 200000000` в 7 файлах — одно и то же «навсегда». Цена: магические потолки и риск тихого выхода по исчерпанию. См. А16; синтаксис — решает автор. [чтение]
2. **`== no` вокруг сравнения** — `os/apps/colony/colony.saltic:72-73,118-119` `((x < left + width) == no) { out no }` (14 раз в файле), `os/uiengine/layout.saltic` (10), `agent.saltic` (8). Нет `>=`/`<=` (уже в PLAN «Мелочи»), и читатель перемножает «не меньше». 50+ строк по ОС с двойной скобкой. [чтение]
3. **Отрицание числа — `0 - value`** — `os/apps/space.saltic` (9), `wire/solids.saltic` (4), `raytrace.saltic` (3): литерал `-18` есть (`parser/syntax.saltic:358-363` — минус склеивается с числом только если стоит вплотную), а `-value` нет. Канон тоже пишет `laps(0 - 1)` (`main.saltic:271`). [чтение]
4. **Биты у обычных чисел через деление** — Б-ОС-2: `num.mod(value / bit, 2) == 1` в двух драйверах, `or16` циклом по 16 битам (`qca9377/boot.saltic:37`); `bits32` не возвращается из навыка и не превращается обратно в число. [чтение]
5. **Нет символа по коду байта** → две таблицы ASCII, одна с искажением (Б-ОС-7), и перебор `CYRILLIC` по байту на каждый символ (`utf8.saltic:21-23`). [чтение]
6. **Имена-уклонения от общих глобальных имён** — **[предп.]**, кодом не доказано: `jtml.prop_words/prop_amount/prop_truth` (`os/uiengine/jtml.saltic:24-36`) вместо `text/number/answer`, `@found`/`@words`/`@amount` как универсальные локальные имена, `disk.minus` вместо `sub`. Похоже на цену известного бага, но может быть и вкусом автора. Явных `the_`/`own_` обходов нет.
7. **Две формы одного адреса на двух платформах**: `os/drivers/*` (qemu_virt) держит адрес как группу `[hi, lo]`, `os/target/uefi_x86_64` — как `Phys {hi, lo}`; `firmware.guest` переводит одну в другую. См. А3. [чтение]
