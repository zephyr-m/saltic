## 1. Плата и чип

ESP32-D0WD-V3 (ревизия 3.1), два ядра Xtensa LX6, 520 КБ SRAM, 4 МБ флеш,
мост CP2102 (`/dev/ttyUSB0`, 115200), на плате MicroPython. Кварц 26 МГц
(досье `docs/site/HARDWARE.html`).

Конфигурация ядра [сеть, `core-isa.h` из esp-idf]: `LX6.0.3`, little-endian,
64 физических регистра (окна), есть DENSITY (16-битные команды), LOOPS,
NSA, MINMAX, SEXT, CLAMPS, MUL16, **MUL32, MUL32_HIGH, DIV32**, MAC16,
BOOLEANS, FP (одинарная точность), S32C1I; **нет** CONST16 и
ABSOLUTE_LITERALS — константы только через `l32r` (пул литералов) или
`movi` + сдвиги. Кэшей у ядра нет (ICACHE/DCACHE = 0 — кэш флеша живёт
снаружи ядра, в SoC). Вектор сброса 0x4000_0400 (ПЗУ).

## 2. Что нужно от Xtensa для договора машины

Договор (`backend.saltic`) — 67 методов. На Xtensa для них хватает core ISA
плюс DENSITY (ради размера; можно и без неё). MUL32/DIV32 для 4-байтного слова
договор не зовёт (рантайм умножает программно, как на RV32I) — запас на потом.

### Команды и их пределы [сеть, ISA Reference Manual; точные числа проверит golden-тест]

| Нужно договору | Команда Xtensa | Предел |
|---|---|---|
| load_immediate | `movi` / `movi.n` | −2048…2047 / −32…95; иначе `l32r` из пула |
| load_address | `l32r` | слово в пуле, патч ABS32 (как у x86) |
| add_immediate | `addi` / `addmi` | −128…127 / кратно 256 до ±32 КБ; иначе через пул |
| and/or/xor_immediate | нет таких команд | константа в регистр (a15), потом `and`/`or`/`xor` |
| shift_left / right | `slli` 1…31, `srai` 0…31, **`srli` только 0…15** | сдвиг вправо > 15 — `extui` (сдвиг 0…31, ширина 1…16) или `ssr` + `srl` |
| shift_*_by (роль) | `ssl`/`ssr` + `sll`/`srl` (через регистр SAR) | — |
| set_less, set_zero… | нет `slt` на LX6 (`salt` — только LX7) | `movi 0; blt… +; movi 1` или `moveqz`/`movltz` |
| load / store | `l32i`/`s32i`, `l16ui`, `l8ui`, `s16i`, `s8i` | смещение **беззнаковое**: 0…1020 / 0…510 / 0…255 |
| branch_* (близкие) | `beq`, `bne`, `blt`, `bge`, `bltu`, `bgeu`, `beqz`, `bnez`, `bltz`, `bgez` | ±127 байт (`beqz`/`bnez` — ±2 КБ) |
| jump | `j` | ±128 КБ |
| jump_far | `jx a9` (SCRATCH1) | — |
| call / ret | `call0` / `ret` | ±512 КБ; цель выровнена на 4 |
| push / pop | `addi a1,-4; s32i` / `l32i; addi a1,4` | — |
| add_checked | нет флага переполнения | как rv32i: `add; xor; xor; and; bltz` |
| syscall(n) | `call0 platform_syscall_<n>` (как x86) | без ловушек и обработчиков |
| wait / fence | `waiti 0` / `memw` | — |
| negate | `neg` | — |
| load_half / byte | `l16ui` / `l8ui` | — |

Размер команд 24 бита (3 байта) и 16 бит (`.n`), выравнивание кода — байт;
только цель `call0` считается от `(PC & ~3) + 4`, поэтому метка навыка —
на границе 4 (`align(CODE, 4)` перед `label`, 0–3 байта `nop`).

### Регистры: окна против call0

- **Windowed** (ABI esp-idf по умолчанию): `call4/8/12` + `entry`/`retw`,
  регистры вращаются, при переполнении окна — исключение, которое
  обрабатывает ПЗУ. Нашему договору это ничего не даёт: роли фиксированы,
  кадр мы строим сами. Зато добавляет обработчики, правила 16-байтного
  стека с запасом под spill и запрет держать роли в «уехавших» регистрах.
- **call0** (без окон): `call0`/`callx0` пишут адрес возврата в `a0`,
  `ret` прыгает по нему. Остальные 14 регистров (`a2`…`a15`) наши целиком,
  `a1` — стек. Это ровно модель rv32i/x86: RETURN = `a0`, store/load RETURN
  — настоящие (как у rv32i с `ra`).

Бюджет ролей при call0 [предп.]: 21 роль, регистров 14. Как у x86 (14 ролей
в регистрах, 5 в памяти): `a2` VALUE, `a3` ERROR, `a4` ARG2, `a5` ARG3,
`a6`…`a11` SCRATCH0…5, `a12` FRAME, `a13` HEAP_TOP, `a14` REGION_MARK;
`a15` — служебный (широкие и отрицательные смещения, литералы, сравнения),
как `t6` у rv32i. В памяти (страница ячеек, как `x86_64_native/roles`):
ARG4…ARG7, ESCAPE_BOTTOM, ESCAPE_MARK. Какой роли отдать `a14`, а какую
спрятать в память — решит исполнитель по горячим циклам рантайма.

### Литералы

`l32r` читает слово по адресу **ниже** команды (до −256 КБ, выровнено на 4).
Сегмент rodata в раскладке идёт после кода — не годится. Самое простое:
пул литералов в начале секции CODE фиксированного размера (резерв нулями,
`layout.set_section_word` уже есть), исполнитель держит таблицу «значение →
смещение» без повторов, адреса меток в пуле — патч ABS32. Код на ESP32 всё
равно ≤ 128 КБ (см. §4), так что один пул достаёт до всего. Переполнился —
пересобрать с пулом побольше (как `far_calls`). Запасной путь без пула —
`movi`+`slli`+`add` ×3 (7 команд, 21 байт на константу) — хуже.

### Смещения

Слоты кадра — ниже FRAME (`constants.local_offset`: отрицательные), а у
`l32i` смещение только 0…1020. Значит каждое обращение к слоту — `addi a15,
a12, -off` (или `addmi`) + `l32i a15, a15, 0`: две команды вместо одной
(как `t6` у rv32i при широких смещениях, но здесь — всегда). Это главная
плата за Xtensa в скорости; лечится позже, если исполнитель будет держать в
`a12` не FRAME, а FRAME − 1024 (смещение в договоре — забота исполнителя).

### Близкие переходы

`branch_*` договора — «близкие», на rv32i ±4 КБ, здесь ±127 байт. Безопасно:
исполнитель всегда ставит обратную ветку через `j` (6 байт вместо 3). Когда
заработает — можно оптимизировать по расстоянию через повтор resolve.

## 3. Образ и загрузка

[сеть, esptool «Firmware Image Format», esp-idf «Bootloader»]

ПЗУ ESP32 (первый загрузчик) читает образ с флеша по адресу **0x1000**,
раскладывает его сегменты в IRAM/DRAM и прыгает на точку входа из заголовка.
Так грузится второй загрузчик esp-idf. **Наш образ может лежать там же** —
никакого esp-idf не нужно, если весь код и данные помещаются в RAM.

Формат (`formats/esp`): заголовок 8 байт (`0xE9`, число сегментов, режим
SPI, размер/частота флеша, точка входа) + расширенный 16 байт (WP-пин,
drive-настройки, chip id = 0 для ESP32, мин./макс. ревизия, флаг SHA-256)
+ сегменты (адрес, длина, данные) + нули до «кратно 16 минус 1» + байт
контрольной суммы (XOR всех байтов данных от 0xEF). SHA-256 — по флагу,
ПЗУ её не проверяет; ставим флаг 0 — тогда esptool спокойно подменит байты
2–3 (режим/размер флеша) при записи по 0x1000. Всё — little-endian. Писатель
— 120–180 строк, без SHA.

Карта памяти [сеть, `bootloader.ld` esp32, TRM]:

| Что | Адреса | Сколько |
|---|---|---|
| IRAM (код + пул литералов + rodata) | 0x4008_0400…0x4009_FFFF | ≈127 КБ (первый 1 КБ — вектора, пропускаем, как esp-idf) |
| DRAM (data, bss, куча, стек) | 0x3FFB_0000…0x3FFD_C200 | ≈176 КБ (выше — ПЗУ и Bluetooth) |
| ещё DRAM | 0x3FFF_0000…0x3FFF_FFFF | 64 КБ «после стека ПЗУ» |
| Кэш-часть SRAM0 | 0x4007_8000…0x4007_FFFF | 32 КБ, пока кэш выключен |

Второе ядро (APP CPU) ПЗУ держит в сбросе — программа одноядерная, думать о
втором не надо.

Ограничение «всё в RAM» [замер]: минимальная программа RV32I с рантаймом —
12 КБ кода+rodata, типичные тесты 16–37 КБ, `json-rpc` 124 КБ, чекер 356 КБ.
Xtensa плотнее RV32I примерно на четверть. То есть hello, smoke, ОС-ядро и
большинство тестов влезают, компилятор — нет. Когда понадобится код во флеше
— ступень «Б»: свой маленький загрузчик в IRAM отображает флеш в окно
0x400D_0000 (IROM, до 3 МБ) и 0x3F40_0000 (DROM) через ПЗУ
(`cache_flash_mmu_set_rom` 0x400095e0, `Cache_Read_Enable_rom` 0x40009a84)
— 80–120 строк, отдельным шагом.

Прошивка: `esptool.py --port /dev/ttyUSB0 write_flash 0x1000 saltic.bin`;
DTR/RTS через CP2102 сами переводят плату в режим загрузки. Запись по 0x1000
стирает второй загрузчик MicroPython — его приложение (0x10000) останется
мусором на флеше; `erase_flash` вернёт чистоту. esptool 5.1.0 есть в nixpkgs
25.11.

## 4. Платформа ESP32 (голое железо)

Как `os/target/qemu_virt/platform.saltic` (256 строк с ловушкой): вход,
вывод, выход, `wait`, остальное — NotSupported.

- **Вход.** ПЗУ прыгает на `entry` с включёнными окнами и обработчиками
  ПЗУ (VECBASE 0x4000_0000 — не трогаем). Ставим `a1` = верх нашего стека в
  DRAM, кладём `[argc, argv]` (`["saltic"]`), `jx _start`. Сторожевые
  таймеры: в режиме SPI-boot ПЗУ включает **RWDT и MWDT0** (так говорит
  TRM и `bootloader_config_wdt` в esp-idf) — перед работой выключить:
  снять защиту ключом 0x50D8_3AA1 (`TIMG0 + 0x64`, `RTC_CNTL + 0xA4`) и
  обнулить `WDTCONFIG0` (`TIMG0 0x3FF5_F000 + 0x48`, `RTC_CNTL 0x3FF4_8000 +
  0x8C`) [адреса — по TRM, сверить]. Иначе плата перезагрузится через ~9 с.
- **Вывод (`write`).** Два пути: (а) функции ПЗУ `uart_tx_one_char`
  (0x4000_9200), `ets_printf` (0x4000_7D54) — они собраны под windowed ABI,
  из call0-кода зовутся `callx4` с аргументом в `a6` и живыми обработчиками
  ПЗУ; (б) напрямую в регистры UART0: FIFO `0x3FF4_0000`, статус
  `+0x1C` (биты 16…23 — занято в FIFO, ждать < 128), делитель `+0x14`.
  Рекомендую (б): ~20 строк, никакого чужого ABI. Адреса ПЗУ пригодятся
  позже для действия `firmware`/`call`.
- **Скорость.** ПЗУ оставляет CPU на кварце (26 или 40 МГц) и APB = кварц;
  UART-делитель считать от 26 МГц (на этой плате — так, иначе лог ПЗУ идёт
  на 74880 бод вместо 115200 — известная примета 26-мегагерцевых плат).
  PLL на 240 МГц — отдельный шаг (esp-idf делает это ~200 строками
  `rtc_clk`), для первого света не нужен.
- **Выход (`exit`).** Печать кода и вечный `waiti 0`, либо `software_reset`
  (ПЗУ 0x4000_824C). **`wait`** — `waiti 0`. `key` — чтение UART0 FIFO (по
  желанию, +15 строк). `now` — счётчик тактов `rsr ccount` (бесплатно, 28
  бит договора).

Где жить (вопрос Q-031): по образцу qemu_virt — `os/target/esp32/`
(`platform.saltic`, `toolchain.saltic`, `smoke.saltic`), писатель образа —
`formats/esp/` или рядом с ELF-писателями в бэкенде.

## 5. Тесты без платы

1. **Кодировщик — golden.** Как `tests/x86-encoder.saltic` +
   `workbench/x86-encoder-golden.saltic` (GNU as из `nixpkgs#binutils`).
   Для Xtensa в nixpkgs 25.11 **ничего нет**: ни `pkgsCross` с xtensa, ни
   `gcc-xtensa-*`, ни `esp-idf`; `lib.systems` не знает cpu `xtensa`.
   Варианты: (а) upstream binutils собрать в `flake.nix` обычным
   `mkDerivation` с `--target=xtensa-esp-elf` (исходник уже в nixpkgs, сборка
   минуты; дефолтная конфигурация ядра может не знать `mull`/`quos` — тогда
   `XTENSA_GNU_CONFIG` = `xtensa_esp32.so` из `espressif/xtensa-dynconfig`,
   ещё один вход флейка); (б) `nixpkgs-esp-dev` (mirrexagon) — готовый
   тулчейн Espressif, скачивание ~100 МБ; (в) без оракула — только по
   таблицам ISA и плате. Рекомендую (а).
2. **Образ.** `esptool.py image_info --version 2 saltic.bin` проверяет
   заголовок, сегменты и контрольную сумму без платы — группа `esp32` в
   `tests/run.sh` рядом с `qemu-virt`/`uefi` (`platforms`).
3. **Эмулятор.** Upstream `qemu-system-xtensa` (в devshell уже есть `qemu`
   10.1.5) знает машины `sim`, `virt`, `lx60`, `kc705`… и ядра `dc232b`,
   `dc233c`, `lx106`, но **не ESP32**. Машина `esp32` — только в форке
   `espressif/qemu` (ветка esp-develop, релизы с готовыми бинарниками для
   linux-x86_64; в nixpkgs его нет). Варианты: (а) форк Espressif —
   деривация в `flake.nix` из исходника (сборка ~15 мин) или их тарболл;
   тогда группа `esp32` гоняет образ так же, как `uefi`: 4-МБ файл флеша
   с нашим `.bin` по 0x1000, `-machine esp32 -nographic -drive
   file=flash.bin,if=mtd,format=raw`, ждём баннер в UART; (б) upstream
   `-machine sim -cpu dc233c` с полувызовами (`simcall`) — ядро LX4 без
   MUL32_HIGH, другая карта памяти: годится проверить исполнитель и рантайм
   на Xtensa вообще, но платформа будет другая (+100 строк); (в) только
   плата. Рекомендую (а), если автор согласен на разовую сборку; до неё —
   (1)+(2) и плата.

## 7. Риски

1. **Пул литералов** — новая механика в исполнителе; размер пула известен
   только в конце → резерв + пересборка. Самый вероятный источник ошибок.
2. **Смещения 0…1020 без знака** — две команды на каждый слот кадра; код
   рантайма на Xtensa будет медленнее rv32i на тактах, пока не введём
   смещённый FRAME.
3. **Сторожа ПЗУ** (RWDT, MWDT0) — не выключили → тихая перезагрузка через
   9 с. Адреса регистров сверить по TRM до первой заливки.
4. **Размер** — всё в RAM: код ≤ 127 КБ, данные+куча+стек ≤ 176 КБ. Куча
   тестов сейчас 512 МБ — для ESP32 нужны кучи ~64–128 КБ; как ведёт себя
   сборщик на такой малой куче — не проверено.
5. **Оракулы** — ни binutils, ни QEMU для Xtensa/ESP32 в nixpkgs: без
   решения по Q-033 кодировщик проверяется только платой.
6. **UART на 26 МГц** — ошибка делителя = мусор в терминале; лечится
   чтением лога ПЗУ на 74880.
7. **Функции ПЗУ — windowed ABI** — если звать их из call0, нужны `callx4`,
   выравнивание стека на 16 и живые обработчики окон. Избегаем, пока пишем
   регистры напрямую.
8. **Первый 24-битный кодировщик** — у нас все команды были 32- или
   байтовые (x86); 3-байтные поля — новый случай для `buffer`/`layout`
   (патчи `l32r`/`call0` считаются в словах от выровненного PC).
