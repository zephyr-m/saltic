# Предложение модели памяти Saltic

**Статус:** архитектурная идея, не принятый канон.

## Основание

Философия Saltic уже закрепляет главное:

- память является ограниченной квотой;
- программа не может выйти за физическую границу;
- при исчерпании она явно просит добавку;
- ядро считает байты и сообщает факт нехватки;
- решение о выдаче памяти принимает слой над ядром;
- GC и mark-and-sweep не используются.

Для долгой работы одного ограничения недостаточно: память должна возвращаться
без поиска недостижимых объектов. Предлагаемое дополнение — иерархические
регионы владения.

## Основная модель

Программа получает корневой регион:

```text
base  — начало доступной памяти
used  — занятые байты
limit — граница квоты
```

Каждый размещённый объект принадлежит одному региону. Внутри региона память
выделяется последовательным bump allocator. Отдельного `free` для объектов нет.
Регион освобождается целиком, когда заканчивается жизнь его владельца.

```text
программа
└── мир
    ├── комната
    │   ├── предмет
    │   └── предмет
    └── временный регион кадра
```

Память принадлежит вещи и исчезает вместе с ней.

## Временная память

Кадр, вызов навыка или другая ограниченная работа получает короткоживущий
регион:

```text
начало работы
→ временные выделения
→ завершение работы
→ сброс всего региона
```

Так игровой цикл может бесконечно повторять временную работу без роста занятой
памяти.

## Изменение долгоживущего состояния

Новое состояние строится отдельно и заменяет старое целиком:

```text
создать дочерний регион
→ построить новое состояние
→ заменить ссылку владельца
→ освободить прежний регион
```

Это даёт повторное использование памяти без обхода графа объектов и без пауз
сборщика мусора.

## Правило ссылок

Долгоживущий объект не может сохранить адрес объекта из более короткого
региона. Компилятор должен выводить времена жизни без обязательных аннотаций в
исходном Saltic-коде.

Если значение должно пережить свой регион, оно переносится или копируется в
регион нового владельца. Конкретное правило переноса остаётся решением
владельца языка.

## Размещение объектов

Объект сохраняет канонический заголовок:

```text
kind
payload_bytes
flags
payload
```

`payload_bytes` позволяет точно учитывать вес и последовательно обходить
объекты региона. Метки GC, счётчики ссылок и индивидуальное освобождение не
нужны.

Raw fixed-значения находятся непосредственно в регистрах, локальных ячейках и
полях подходящей ширины. Они не требуют heap-объекта.

## Исчерпание квоты

Если очередной объект не помещается, allocator не расширяет память сам. Он
возвращает через канонический `rescue` факт нехватки как минимум с такими
данными:

```text
requested — сколько байт потребовалось
used      — сколько уже занято
limit     — текущая граница
```

Слой над ядром решает, выдать ли новый участок, отказать, сохранить состояние
или обратиться к пользователю. Уже размещённые объекты не перемещаются.

## Почему эта модель подходит Saltic

- Один основной путь выделения памяти.
- Явная физическая квота.
- Предсказуемое время выполнения.
- Нет скрытых остановок GC.
- Адреса объектов стабильны.
- Память освобождается понятными областями владения.
- Модель не зависит от Linux, QEMU или конкретного процессора.
- Иерархия памяти соответствует миру, состоящему из вещей и их содержимого.

Единая bump-куча без регионов со временем исчерпывается. Индивидуальный `free`
добавляет второй путь и фрагментацию. Регионы сохраняют простоту bump allocator,
но дают контролируемые границы повторного использования.

## Решения, которые остаются за владельцем

- Что именно создаёт долгоживущий регион: каждая вещь, сцена или более крупный
  владелец.
- Является ли временный регион границей кадра, навыка или явного блока.
- Используется перенос или копирование при выходе значения из региона.
- Как слой над ядром выдаёт и возвращает физические участки памяти.
- Какая форма данных передаётся в `rescue` при исчерпании квоты.

## Грубая оценка реализации

Без анализа текущего кода:

| Часть | Оценка |
|---|---:|
| Базовые регионы, квоты, выделение и сброс | 400–700 строк |
| Иерархия владельцев и возврат памяти | 300–600 строк |
| Правила времени жизни в компиляторе | 700–1400 строк |
| `rescue` при нехватке памяти | 150–300 строк |
| Интеграция с runtime и объектами | 400–800 строк |
| Проверки | 400–800 строк |
| **Полная модель** | **2350–4600 строк** |

Минимальная рабочая версия без строгой проверки ссылок компилятором оценивается
в 900–1500 строк, но будет полагаться на дисциплину кода.
