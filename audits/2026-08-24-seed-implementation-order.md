# Порядок реализации закрытия seed

**Дата:** 24 августа 2026 года

**Основание:** полный аудит seed и решения владельца проекта.

## Решение

Не открывать сразу два крупнейших новых фронта — типизацию и GC, пока не готовы
machine/image-контур и независимые от ABI части VM. Machine/image-контур уже
закрыт 24 августа; теперь выполняется машинная часть VM. Типы и память идут
после устойчивого общего machine/VM-основания, но до финального перевода
compiler/runtime и доказательства замкнутости.

## Порядок работ

1. **Полностью закрыть пункт 5 — machine/image — `ГОТОВО 24.08.2026`.**
   - квадратичный Buffer заменён на chunked/random-access представление;
   - таблица 44 команд создаётся один раз и переиспользуется;
   - labels и patches переведены с растущих persistent-групп на связанные структуры;
   - ELF записывается chunks без повторной плоской группы байтов;
   - удалён `machine/program.saltic`: это был дубль, владельцем раскладки остался `machine/layout.saltic`;
   - независимыми тестами закреплены golden bytes всех 44 команд, границы immediate и семь patch kinds;
   - проверена структура host/virt ELF и payload 64 KiB на границах chunks;
   - один созданный собственным image-builder host ELF выполнен и собственной VM, и `qemu-riscv32`;
   - `just stage-3-machine`: 132 machine-проверки + 4 VM-проверки, 0 провалов, QEMU exit 0.

2. **Подтянуть независимую машинную часть VM из пункта 7 — `СЛЕДУЮЩИЙ`.**
   - использовать общий профиль 44 команд;
   - реализовать `csrrw`, `csrrs`, `mret`, `wfi`;
   - поддержать полное 32-битное адресное пространство, включая `0x80000000`;
   - убрать ручное дублирование машинной таблицы и подготовить process/machine modes;
   - не привязывать эту работу к ещё не реализованному ABI значений.

3. **Создать единое типизированное представление программы — `НЕ ЗАКРЫТО`.**
   - реализовать принятый межпроцедурный мономорфный вывод типов;
   - один `skill` получает одну сигнатуру входа и выхода;
   - несовместимые вызовы и неразрешённая неоднозначность дают диагностику;
   - compiler потребляет результат checker, а не повторяет собственный частичный вывод.

4. **Реализовать настоящий ABI и перевести compiler/runtime на машинное представление — `НЕ ЗАКРЫТО`.**
   - raw fixed передаются по выведенной сигнатуре;
   - `a0` содержит значение, `a1` — отдельный raw error id;
   - применить единый object layout;
   - удалить assembly strings и GNU `.s` путь, не оставляя параллельный backend.

5. **Реализовать память после появления типов и ABI — `НЕ ЗАКРЫТО`.**
   - записывать 16-байтовые object headers;
   - compiler публикует точные managed roots;
   - runtime выполняет неперемещающий mark-and-sweep;
   - освобождённые блоки используются повторно;
   - длительный сценарий проходит на намеренно маленькой heap без накопительной утечки.

6. **Собрать две платформенные композиции — `НЕ ЗАКРЫТО`.**
   - общее program/runtime body;
   - host ELF для process-mode VM и `qemu-riscv32`;
   - qemu-virt ELF для machine-mode VM и `qemu-system-riscv32`;
   - одинаковый наблюдаемый результат одного ELF в собственной VM и соответствующем QEMU;
   - удалить `linux-memory.S` и `platform.S` после появления Saltic-owned замены.

7. **Закрыть bootstrap и пункт 8 — `НЕ ЗАКРЫТО`.**
   - прямой ELF stage 1 → stage 2 → stage 3 без промежуточного `.s`;
   - stage 2 и stage 3 совпадают побайтово;
   - каноническая программа собирается и исполняется закрытым toolchain;
   - удалить GNU assembler/linker/objcopy из build/test recipes;
   - удалить `tests/fixtures/vm-canonical.S` и остальные остатки старого пути;
   - пройти все восемь gate’ов командой `just seal` из `soul/seed`.

## Важное различие

Порядок gate’ов в `soul/seed/justfile` отражает причинную цепочку доказательства: язык → ABI → машина → образ → память → host → virt → closure. Он не обязан совпадать с порядком написания кода.

`stage-3-machine` теперь зелёный и является доказательством завершения шага 1.
Следующая практическая работа — шаг 2: независимая машинная часть VM. Типизация
и GC по-прежнему не открываются раньше устойчивого общего machine/VM-основания.

## Выполненная поддерживающая работа bootstrap

При закрытии шага 1 потребовалось обновить зафиксированный compiler с новым
chunk-aware runtime. Выполнено:

- общий переходный linker-path вынесен в `os/bootstrap/link.sh` и используется
  `os/bootstrap/build.sh`;
- стандартная heap сборки и тестового helper поднята с 16 MiB до 512 MiB;
- `os/bootstrap/refresh.sh` получил автоматический вход в Nix shell и rescue-путь
  с heap `4026531840`; этот размер применяется ко всем трём поколениям refresh;
- rescue compiler успешно провёл stage 1 → stage 2 → stage 3 и fixed-point check;
- обновлён `os/bootstrap/compiler.elf`, SHA-256
  `7135ef47b583bc3e56773dc7797f2b70c710cb43a4d7e6d467dfe48047fe2a27`;
- в корневой `justfile` добавлена воспроизводимая команда `bootstrap-rescue`.

Это обслуживание действующего GNU-based bootstrap, а не досрочное выполнение
шага 7. Прямой ELF fixed point и удаление GNU toolchain остаются незакрытыми.
