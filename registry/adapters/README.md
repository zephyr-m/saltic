# Реестр адаптеров

Адаптеры Saltic (драйверы — адаптеры железа) живут здесь, по платформам:
у каждого своя папка: `registry/adapters/<платформа>/<имя>/<имя>.saltic`,
там же паспорт `<имя>.passport.json` и подмодули (решение автора 17.11.2026; переезжают по одному — пока здесь `esp32/` и
`android/`, драйверы Acer ещё в `os/target/uefi_x86_64/drivers/`). Реестр
знает, где каждый, и сверяет паспорт с кодом. Позже реестр станет источником для пакетного
менеджера «tarantul». Папка самостоятельна: потом уедет в свой репозиторий,
отдельно от реестра библиотек (`registry/libraries/`).

| файл | что это |
|---|---|
| `adapters.txt` | список: имя и путь без расширения; код — `<путь>.saltic` и папка `<путь>/`, паспорт — `<путь>.passport.json` |
| `index.json` | индекс, его пишет `just registry`: имя, заголовок, пути, число файлов кода, идентификаторы, своя версия, архитектуры, эффекты по коду, состояние, итог и замечания |

## Паспорт

`<имя>.passport.json` — объект JSON (решение автора 17.11.2026): ключи —
английские, это формат; значения — по-русски, это текст для человека. Читает
`workbench/passport.saltic` (сверка и tarantul). Поля — как у всех паспортов:
`title` (что это), `saltic_version` (в составе какого Saltic вышел),
`author`, `role` (`adapter`), `lifetime`, `deadline`, `effects`, `hardware`,
`protocols`, `architectures`, `primitives`, `depends_on`, `environment`,
`state`, `filled_by` — и ещё три для реестра:

- `identifiers` — по чему адаптер узнаёт своё железо, в машинном виде,
  через запятую: `pci 10ec:8168` (vendor:device), `usb 0408` (vendor),
  `uefi simple-pointer` (протокол прошивки), `i2c 78` (адрес на шине I2C со
  сдвигом), `esp32 i2c0` (блок чипа ESP32), `android camera2-front` (служба
  Android);
- `own_version` — версия самого адаптера, растёт при правке его кода; по ней
  tarantul привозит пакет и стережёт замок;
- `log` — что адаптер пишет в журнал (сам или через агента), чтобы поломку
  на железе читать по журналу, а не гадать; не пишет — «нет» и куда уходит
  ошибка (решение автора 11.11.2026).

## Сверка — `just registry`

Проверяет каждый адаптер списка (устройство — `workbench/registry.saltic`):

1. паспорт есть, все поля на месте, роль — «адаптер»;
2. архитектуры из паспорта известны, и адаптер лежит в папке своей платформы;
3. код чист у `lens check`: разбор, чекер, лимиты канона — у главного файла
   и у всех `*.saltic` в папке адаптера;
4. эффекты: заявленное совпадает с выведенным из кода — нашёл своё устройство
   и пишет в него → «пишет в железо» (на ESP32 устройство по адресу: пишет в
   регистры — тоже), иначе «только читает»; пишет файлы → в паспорте должен
   быть «диск»;
5. идентификаторы `pci`, `usb` и `i2c` стоят константами в коде; `uefi`,
   `esp32`, `android` — имена, сверять нечего.

Архитектуры: `x86_64-uefi` (Acer, пока `os/target/uefi_x86_64/`),
`xtensa-esp32` (DevKit, `registry/adapters/esp32/`), `arm64-android` (телефон,
`registry/adapters/android/`) — адаптер лежит в папке своей платформы.

Провал — замечания по адаптеру и ошибка `RegistryBroken`. Новый адаптер:
паспорт рядом с кодом, строка в `adapters.txt`, `just registry`.

Пределы сегодня: эффекты выводятся по вызовам платформы, а не по потоку
данных; константа идентификатора ищется в тексте как `= число`.
